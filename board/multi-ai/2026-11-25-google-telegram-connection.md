# 서버의 AI 에이전트를 구글 캘린더·구글 도구·텔레그램과 연결하기 (비전문가용 매뉴얼)

> 이 글은 2026년 10월 말~11월 초에 서버(Ubuntu)의 AI 에이전트(Hermes Agent)를 텔레그램과 구글 서비스에 연결한 작업 기록 5편을 읽고 정리한 것입니다. **실제로 해 보고 결과를 확인한 것**과 **보고만 받았거나 아직 못 해 본 것**을 나누어 적었습니다. 이메일·IP·계정 이름·봇 이름·각종 ID·비밀번호·토큰은 모두 `<구글_계정>`처럼 자리표시자로 바꾸었으며, 원본에 값이 있어도 옮기지 않았습니다.

## 0. 먼저 읽기

### 0.1 결론부터

| 질문 | 답 |
|---|---|
| 무엇을 연결했나 | 서버의 AI 에이전트 ↔ 텔레그램(대화창), 서버의 AI 에이전트 ↔ 구글 캘린더·드라이브·시트 |
| 되는 것 (직접 확인) | 텔레그램에서 AI에게 말하면 캘린더 조회, 시트 읽기·승인된 칸 수정, 예약 알림 수신 (PC와 스마트폰 모두) |
| 아직 안 되는 것 | 캘린더에 일정을 적기만 하면 저절로 텔레그램 알림이 오는 기능 (계획만 함, 미구현) |
| 가장 조심할 것 | 로그인(OAuth) 비밀값이 채팅·캡처·공개 저장소에 새어 나가지 않게 하는 것 |
| 큰 약점 | AI가 구글 자료를 바꾸기 전에 "승인을 받는다"는 약속은 **지침일 뿐 기술적으로 강제되지 않음** |

### 0.2 이 글의 자리표시자

| 자리표시자 | 뜻 |
|---|---|
| `<구글_계정>` | 연결에 쓴 본인의 구글 계정(이메일) |
| `<프로젝트_이름>` / `<프로젝트_ID>` | 구글 클라우드에서 만든 프로젝트의 이름 / 고유 번호 |
| `<클라이언트_ID>` / `<클라이언트_비밀번호>` | 로그인 허용 신청서(OAuth 클라이언트)의 번호 / 비밀 열쇠 |
| `<토큰>` | 로그인 상태를 담은 열쇠 (아래 용어 풀이 참조) |
| `<서버_사용자>` / `<서버_주소>` | 서버의 사용자 이름 / 접속 주소 |
| `<텔레그램_봇>` / `<작업방>` | AI가 대화에 쓰는 봇 / 텔레그램 대화방 |
| `<시트_ID>` | 테스트용 스프레드시트의 고유 번호 |

### 0.3 어려운 말 한 줄 풀이

- **OAuth**: 내 비밀번호를 AI에게 주지 않고, "이 프로그램이 이 범위까지만 내 구글을 써도 된다"고 구글에 허락해 주는 방식.
- **토큰(액세스 토큰)**: 허락의 증표. 짧게(약 1시간 안팎) 쓰고 만료됩니다.
- **리프레시 토큰**: 만료된 액세스 토큰을 새로 바꿔 받는 열쇠. 이것이 새면 위험합니다.
- **범위(scope)**: 허락해 준 일의 목록(예: 캘린더 보기, 메일 보내기).
- **게이트웨이**: 텔레그램 메시지를 서버의 AI에게 전달해 주는 서버 쪽 프로그램.
- **API**: 프로그램끼리 서로 일을 시키는 창구. 구글 서비스마다 따로 켜야 합니다.

### 0.4 실제로 한 것과 계획만 한 것

- **실제로 함**: 구글 클라우드 설정, 로그인 허락, 캘린더·드라이브·시트 호출, 텔레그램 송수신, 예약 알림 4건 수신.
- **보고로만 확인**: 테스트 중 일부 결과(하위 AI의 시트 수정 세부 출력, 로그인 앱의 운영 상태 전환 등)는 AI나 사용자의 보고에 근거합니다.
- **계획만 함**: 캘린더 자동 감지 알림, 승인 강제 장치, 대용량 드라이브 검색 최적화.

## 1. 준비

1. **서버**: AI 에이전트가 이미 설치되어 있고, 텔레그램과 대화하는 게이트웨이가 켜져 있어야 합니다.
2. **내 PC**: 서버에 원격 접속할 수 있어야 하고(작업 기록에서는 PC의 터미널에서 접속), 크롬 브라우저가 필요합니다.
3. **구글 계정**: 연결할 본인 계정 1개.
4. **원칙(기록에서 계속 지킨 것)**:
   - 명령은 한 번에 하나씩, **어느 컴퓨터에서 치는지**(내 PC인지 서버인지) 먼저 확인합니다.
   - 정상 작동 중인 설정은 건드리기 전에 백업합니다.
   - 유료 API 결제 계정은 연결하지 않았습니다(작업 당시 결제 계정 미연결 확인).

> 서버 안 파일 위치는 `~/.hermes/` 아래(홈 폴더의 숨김 폴더)입니다. 사용자 이름이 들어간 전체 경로는 적지 않았습니다.

## 2. 1단계 — 텔레그램과 서버 AI 연결 확인

**왜**: 모든 조작을 휴대폰 대화창으로 하기 위해서입니다.

**무엇을**: 서버의 게이트웨이 서비스가 켜져 있는지 읽기 전용 명령으로 확인했습니다.

```bash
systemctl --user status hermes-gateway.service --no-pager
```

**확인된 결과**
- `active (running)` 이고 부팅 시 자동 시작(`enabled`) 상태.
- 스마트폰 텔레그램에서 송수신 성공, PC 텔레그램에서도 테스트 메시지 송수신 성공.
- 처음엔 폰 대화가 PC에 안 보였으나, **같은 전화번호 계정으로 로그인했는지** 확인하니 동기화되었습니다.
- 로그에 연결 오류 경고가 있었지만 실제 송수신은 성공했습니다. 재발 여부는 관찰 중(미확인).

### 2.1 답변이 조금씩 나오게 하기

설정 파일의 스트리밍 항목을 `false`에서 `true`(전송 방식 `edit`)로 바꾸고 게이트웨이를 다시 시작했습니다. 바꾸기 전 설정 파일을 백업했고, 사용자가 "조금씩 나옴"을 직접 확인했습니다. 이 방식은 같은 메시지를 여러 번 고쳐 쓰는 것이라 글자 단위 실시간은 아닙니다.

## 3. 2단계 — 구글 클라우드에서 로그인 허락 준비

**왜**: AI가 내 구글을 쓰려면 구글에 "이 앱을 허락한다"고 등록해야 합니다.

**무엇을** (모두 내 PC 크롬에서):

1. 구글 클라우드에서 새 프로젝트(`<프로젝트_이름>`) 만들기.
2. 쓸 서비스의 API 켜기 — 처음엔 캘린더·드라이브·시트. (메일 API는 4단계 참조)
3. OAuth 동의 화면 설정: 사용자 유형 `외부(External)`, 테스트 사용자에 본인 계정 1명 추가.
4. OAuth 클라이언트 만들기: 종류 **데스크톱 앱**. 만들면 `<클라이언트_ID>`와 `<클라이언트_비밀번호>`가 든 파일을 내려받을 수 있습니다.

**확인된 결과**: 결제 계정이 연결되지 않은 상태로 진행했고, 동의 화면에는 앱 이름이 표시되며 사용자 동의까지 완료했습니다.

## 4. 3단계 — 서버에 로그인 허락 완료하기

**왜**: 구글이 준 허락을 서버의 AI가 쓸 수 있게 서버 파일로 저장해야 합니다.

**무엇을** (서버에서):

1. 서버의 AI에 구글 도구용 부품을 설치(`hermes pm install --extra google`) → 준비 완료 표시 확인.
2. 내려받은 클라이언트 파일을 서버의 `~/.hermes/` 아래에 두고, 스킬(구글 도구 모음)이 제공하는 설정 스크립트로 인증 주소를 만듦.
3. 내 PC 브라우저에서 그 주소를 열어 구글에 로그인·동의.
4. 동의 후 브라우저가 이상한 주소로 이동하며 **오류 화면(ERR_UNSAFE_PORT)** 이 뜨는데, 이것은 실패가 아닙니다. 주소창에 남은 `code=` 값을 서버의 설정 스크립트에 넘겨(`--auth-code`) 마무리했습니다.
5. 확인 명령 두 가지:
   - `--check`: 토큰 파일이 유효한지 → `AUTHENTICATED`
   - `--check-live`: 실제로 구글에 한 번 물어보기 → `LIVE_CHECK_OK`

**확인된 결과**: 두 확인 모두 성공했고, 토큰 파일에는 클라이언트 정보·리프레시 토큰·만료 시각·허락 범위 8개(캘린더, 문서, 연락처 읽기, 드라이브, 메일 수정·읽기·보내기, 시트)가 들어 있음을 **값은 출력하지 않고 항목만** 확인했습니다.

> 주의: 토큰에 범위가 적혀 있다고 해서 그 기능이 실제로 작동한다는 뜻은 아닙니다. 작동은 하나씩 따로 시험해야 합니다.

## 5. 4단계 — 서비스별로 실제 시험하기

| 서비스 | 한 일 | 결과 | 구분 |
|---|---|---|---|
| 캘린더 | 목록·7일 일정 조회 | 성공 (캘린더 2개: 공휴일, 기본). 기본 캘린더 7일치가 비어 있어 `[]`로 나온 적 있음 | 직접 확인 |
| 드라이브 | 파일 검색, 첫 5개 목록 | 성공. 정렬 없는 첫 5개이며 전체 목록 아님. 내용 열람·수정 없음 | 직접 확인 |
| 시트 | 테스트 문서 생성, 칸 입력, 읽기, 한 칸 수정 | 성공. 문서는 내 드라이브에 생김(서버 로컬 파일 아님) | 직접 확인 |
| 상위 AI → 하위 AI 위임 | 상위 AI가 하위 AI(다른 회사 모델)에게 캘린더 조회·시트 읽기·한 칸 수정을 맡김 | 서버 기록상 완료. 시트 세부 출력은 상위 AI의 로그 열람 보고에 근거 | 일부 보고 |
| 메일(Gmail) | 처음 호출 시 HTTP 403 | 원인: 구글 클라우드에서 메일 API가 꺼져 있었음 → 사용자가 직접 `사용` 클릭 | 켜기까지만 확인 |
| 메일 재시험 | 사용자 프로필 조회 1회 | **미확인** (다음 단계로 남음) | 미확인 |
| 문서(Docs)·연락처 | — | **미확인** | 미확인 |

시트 시험은 칸마다 승인을 받고 했습니다. 상위 AI는 한 칸, 하위 AI도 다른 한 칸만 수정했고, 다시 읽어 값이 맞는 것까지 확인했습니다. 시험용 문서는 삭제하지 않고 보존했습니다.

## 6. 5단계 — 캘린더 일정을 텔레그램 알림으로 받기

**왜**: 캘린더에 적어 둔 일정을 폰으로 알려 주게 하려고 했습니다.

**무엇을**: 사용자가 캘린더에 일정을 직접 입력 → AI가 캘린더에서 제목·시간·상세 설명을 조회 → 서버 AI의 일회성 예약으로 텔레그램 발송을 걸어 둠(수동 연결 방식).

**확인된 결과**
- 11월 1일 저녁 실습 알림 **4건 모두** PC와 스마트폰에서 수신 확인.
- 예약 시각보다 약 1분 늦게 도착했습니다.
- 마지막 알림에는 일정 제목과 상세 설명이 모두 들어 있었습니다.
- 사용자가 실수로 만든 `제목 없음` 일정도 알림이 왔고, 삭제는 승인되지 않아 **임의로 지우지 않았습니다.**
- "짧게 지시하면 안 걸어 둔 일정을 추가 예약"하는 것도 되었으나, 날짜 범위를 말하지 않아 **다음 날 일정까지 예약**되었습니다. → 항상 날짜 범위를 함께 말하세요.

**아직 안 된 것(미구현·미검증)**
- 캘린더에 입력만 하면 자동으로 알림이 오는 기능: 구현하지 않음. 계획은 "일반 프로그램이 주기적으로 읽기 전용으로 조회해 발송" 구조(AI를 매번 부르지 않아 사용량 절약)였으나 **계획 단계**입니다.
- 일정을 고치거나 취소했을 때 예약이 따라 바뀌는 동기화: 미구현.
- 할 일(Tasks), 약속 일정: 미검증.
- 다음 날 예약 3건의 수신 결과는 자료에 없음 → **미확인**.

## 7. 6단계 — 7일 만료 문제와 운영 전환

**문제**: 동의 화면이 `외부 / 테스트 중`이면, 캘린더·드라이브 같은 범위를 쓰는 로그인 열쇠(리프레시 토큰)가 **약 7일 뒤 만료**될 수 있습니다. 처음 승인일 기준 11월 8일 전후가 위험 시점이었습니다.

**조치(11월 3일 기록)**: 동의 화면을 테스트에서 **운영(Production)** 으로 전환하고, 새 리프레시 토큰을 받아 범위 8개 확인, 캘린더 호출 성공, 액세스 토큰 자동 갱신 성공이라고 **보고**되었습니다.

**운영 전환을 위해 한 일**: 앱 이름, 지원 연락처 외에 개인정보처리방침 주소 등이 필요해, 공개 웹페이지(정적 홈페이지)에 안내 페이지와 개인정보처리방침 페이지를 마련했습니다. 이 페이지에는 비밀값을 올리지 않습니다.

**해석할 때 주의**
- "자동 갱신 성공"은 "영원히 재로그인이 필요 없다"는 뜻이 아닙니다. 토큰 폐기, 권한 변경, 구글 보안 정책에 따라 다시 로그인할 수 있습니다.
- 운영 전환 후 드라이브·시트 재검증은 **미확인**입니다.
- 이후(11월 5일) 자료에서도 "자동 갱신이 실제로 일어나는지"는 여전히 미완료 항목으로 남아 있습니다. 즉 **보고는 있으나 장기 확인은 아직 없음**입니다.
- 로그인 과정의 실패는 구글 문제라기보다, PC에서 서버로 코드를 붙여 넣을 때 **클립보드가 덮어써지거나 일회용 코드가 만료**된 것이 원인으로 분석되었습니다(분석 기준, 확정은 아님). 주소를 다시 만들어 입력해 성공.

## 8. 보안 주의 (이 글에서 가장 중요)

### 8.1 로그인 정보 보관

1. **채팅·캡처·공개 저장소에 올리지 않기.** 이번 작업에서 처음 발급한 클라이언트 비밀번호와 일회용 인증 코드가 과거 채팅·화면에 노출된 일이 있었습니다. 그래서 새 비밀번호를 만들고 옛것을 **사용 중지 → 삭제**했으며, 삭제 뒤에도 `--check-live`가 성공함을 확인했습니다. (비밀번호가 새면 이렇게 교체하세요.)
2. 인증 후 주소창의 전체 주소(`code=` 포함)도 비밀로 취급합니다.
3. 서버의 인증 파일(클라이언트 파일, 토큰 파일)은 **글자 그대로 문서에 적지 않습니다.** 백업 폴더는 소유자만 접근하게(폴더 700, 파일 600) 관리했다고 보고되었습니다.
4. 인증 파일은 일반 마크다운·평문 백업에 넣지 말고 **암호화 백업**에만 둡니다.
5. 내려받은 클라이언트 파일 사본이 PC 다운로드 폴더와 서버 홈에 남아 있을 수 있습니다. 전수 조사는 **미완료**이므로, 현재 쓰는 파일과 구별해 승인 후 정리하세요. 현재 쓰는 인증 파일을 지우면 안 됩니다.
6. 공개 저장소(웹 호스팅용)에는 키, 비밀번호, 토큰, 접속 정보, 개인 자료를 올리지 않습니다.

### 8.2 권한 범위

- 동의한 범위가 넓습니다(메일 읽기·수정·보내기, 드라이브 전체, 문서, 연락처 등 8개). 쓰지 않는 범위까지 열려 있으므로 **최소 권한 원칙**상 부담입니다. 범위 축소는 계획·검토 대상일 뿐 **아직 하지 않았습니다**.
- 메일은 API를 켠 것까지만 했습니다. 처음 시험은 **프로필 조회 1회**로 제한하고, 메일 목록·본문 열람, 발송·수정·삭제는 하지 않기로 했습니다.

### 8.3 AI의 승인 약속은 기술적 보호가 아님

- 구글 도구 스킬의 지침에는 "메일 발송, 일정 생성·삭제, 파일 공유·삭제, 문서·시트 수정 전에 사용자에게 확인"이 적혀 있습니다.
- 그러나 시트 수정 함수를 살펴보니 **승인 여부를 검사하는 코드가 없고** 곧바로 구글에 호출합니다. 시험에서 AI들이 승인된 칸만 고친 것은 **지침을 지킨 것**이지, 막혀서가 아닙니다.
- 서버 설정의 `skills.write_approval`은 **스킬(AI의 능력 파일) 생성·변경** 승인이며, 구글 자료 수정 승인과는 별개입니다. 혼동하지 마세요.
- 해결 방안(승인 게이트, 더 좁은 권한, 별도 시험 환경)은 **검토만 했고 구축하지 않았습니다.**
- 그래서 지금은 사람이 지킵니다: 대상·범위·영향을 말한 뒤 **명시적으로 "승인"** 해야 일을 시키고, 삭제는 휴지통 방식 선호, 위험한 승인 우회 시험은 하지 않습니다.

### 8.4 비용·그 밖의 주의

- API를 켜는 것 자체가 곧바로 요금은 아닙니다. 다만 AI가 메일 등을 분석하면 **AI 쪽 사용량(구독 한도나 API 요금)이 별도로** 쓰입니다.
- 드라이브 자료가 매우 커서(사용자 설명 약 2.5TB), 매번 전체를 검색해 AI에 넘기지 않아야 합니다. 최적화(파일명·폴더 우선 검색, 결과 수 제한, 선택 파일만 분석)는 **보류 상태**입니다.
- 서버에 주 목적 설정(게이트웨이, 허용 사용자, 인증 파일)을 승인 없이 바꾸거나 재시작하지 않습니다.

## 9. 막혔던 일과 해결

| 막힌 일 | 원인(확인 정도) | 해결 |
|---|---|---|
| 로그인 후 브라우저가 오류 화면(안전하지 않은 포트) 표시 | 구글이 보낸 임시 주소가 브라우저에서 막힘 — 실패 아님 | 주소창의 `code=` 값을 서버 스크립트에 넘겨 마무리 |
| 인증 코드 입력 실패 | PC→서버 붙여 넣기 중 클립보드 덮어쓰기, 일회용 코드 만료(분석) | 인증 주소를 다시 만들어 재시도, 성공 보고 |
| 옛 클라이언트 비밀번호 노출 | 과거 채팅·화면에 보임 | 새 비밀번호 발급 → 옛것 사용 중지 → 삭제 → 실제 호출 재확인 |
| 메일 호출 HTTP 403 | 구글 클라우드에서 메일 API가 꺼져 있음 | 사용자가 직접 `사용` 클릭(재시험은 미확인) |
| 캘린더 조회 결과가 `[]` | 기본 캘린더 7일간 일정이 없었음 | 오류 아님. 다른 캘린더는 별도 지정 필요 |
| 폰 대화가 PC에 안 보임 | 다른 텔레그램 계정으로 로그인했을 가능성 | 같은 전화번호 계정 확인 후 동기화 |
| 7일 뒤 로그인 만료 우려 | 동의 화면이 외부/테스트 중 | 운영 전환 + 새 토큰 (보고 기준, 장기 확인 미완) |
| 홈페이지 접속 시 404 | 배포 반영 지연 | 잠시 기다린 뒤 새로고침, 중복 업로드 금지 |

## 10. 확인하지 못한 것 (미확인 목록)

1. 메일 API 프로필 조회 재시험 결과.
2. 문서(Docs)·연락처(Contacts) 작동.
3. 운영 전환 후 드라이브·시트 재검증.
4. 리프레시 토큰이 장기간 정말 유지되는지, 자동 갱신이 실제로 반복 수행되는지.

6. 캘린더 입력만으로 되는 자동 알림, 수정·취소 동기화, 할 일(Tasks) 연동.

8. 예전 클라이언트 파일 사본의 전수 조사와 정리.

10. 텔레그램 연결 경고 로그의 재발 여부와 원인.
11. 암호화 백업의 복원 시험(복원 리허설 완료로 보면 안 된다고 기록됨).

## 11. 한 줄 정리

**텔레그램에서 서버 AI에게 말해 캘린더·드라이브·시트를 조회하고 승인된 시트 칸을 고치는 것까지는 실제로 성공했지만, 로그인 비밀값은 절대 밖으로 내보내지 말고, AI의 "승인받겠다"는 약속은 기술적 보호가 아니므로 사람이 직접 승인을 지켜야 하며, 메일·문서·연락처·장기 토큰 유지·자동 알림은 아직 확인하지 못했다.**
