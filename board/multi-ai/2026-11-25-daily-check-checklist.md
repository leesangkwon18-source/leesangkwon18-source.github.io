# AI 협업팀 매일 점검 매뉴얼 — 무엇을 보고, 어떻게 판정하고, 이상하면 어떻게 하나

> 이 글은 2026년 11월 21일~24일에 실제로 쓴 매일 점검표와 인수인계 기록을 쉬운 말로 다시 정리한 것입니다. **확인된 것**: 서버용 점검표(자동 항목 15개와 충돌 항목 7개)와 폰용 점검표가 실제로 만들어져 쓰였고, 폰 점검 스크립트는 11-22에 시험 실행해 정상 값을 읽었으며, 11-24에는 케이블 없이 터널로 하는 점검도 성공했습니다. **못한 것**: 백업 복원 시험, 서버 재부팅 뒤 자동 시작 확인, 크레딧·잔액의 자동 확인은 한 번도 하지 못했습니다(이 글 끝의 "확인하지 못한 것" 참고).

## 0. 먼저 읽기

**결론부터**: 매일 아침 5~10분이면 됩니다. 점검은 AI 도우미(Claude)가 서버를 읽어서 하고, 사람은 **화면으로만 볼 수 있는 숫자(비용·잔액)를 확인하고 이상할 때 결정**만 합니다. 점검은 **읽기 전용**이라 서버에 아무것도 쓰지 않습니다.

**이 글의 대상**: 서버에서 AI 여러 명(Claude 계열, GPT 계열, Gemini 계열)이 텔레그램으로 협업하는 "AI 협업팀"을 처음 관리하는 사람입니다.

**용어 한 줄 풀이**

| 용어 | 뜻 |
| --- | --- |
| 게이트웨이 | AI와 텔레그램을 이어 주는 프로그램. 이게 멈추면 봇이 답하지 않음 |
| 에이전트(역할) | 팀원 한 명에 해당하는 AI. 어느 회사 모델이 어떤 임무를 맡는지 |
| 프로필 | 팀원 한 명의 "자기 집". 지침·기억·로그인·설정이 따로 들어 있음 |
| 지침(SOUL) | AI에게 주는 행동 규칙 문서 |
| 해시 | 파일 내용의 "지문". 한 글자라도 바뀌면 값이 달라져서 몰래 바뀐 것을 잡는 데 씀 |
| 토큰·키 | 서비스에 들어가는 비밀 열쇠. 채팅에 쓰지 않음 |
| 크레딧 | 미리 받은 AI 사용 금액. 0이 되면 해당 키가 멈춤 |
| 터널 | 폰이 서버 쪽으로 먼저 열어 둔 보안 통로. 이를 통해 점검함 |

**자리표시자**: 이 글의 명령에는 실제 서버 주소, 계정 이름, 봇 이름이 들어가지 않고 `<서버_주소>`, `<내_계정>`, `<게이트웨이_서비스_이름>`처럼 적혀 있습니다. 실제 값은 관리자에게 받아 **본인이 직접 바꿔서** 입력하세요. 꺾쇠(`<` `>`)까지 지우고 바꿔야 합니다.

**지켜야 할 원칙 세 가지**
1. 점검 중에는 **보고만** 하고 서버를 고치지 않습니다. 재시작·삭제도 사람이 승인한 뒤에만 합니다.
2. 키·토큰·비밀번호는 채팅에 쓰거나 화면을 캡처해 보내지 않습니다.
3. 모르는 것은 "미확인"이라고 적습니다. 짐작은 "추정"이라고 표시합니다.

## 1. 왜 매일 점검하나

AI 협업팀은 겉으로 멀쩡해 보여도 **조용히 멈추거나 바뀔 수** 있습니다. 실제 기록에서 확인된 위험은 다음과 같습니다.

| 위험 | 실제 기록 | 매일 보는 이유 |
| --- | --- | --- |
| 크레딧 소진 | 결제 수단이 없어서 크레딧이 0이 되면 카드 청구 없이 **모든 키가 조용히 정지**. 크레딧 한 묶음이 11-24 09:00에 소멸 예정이었음 | 미리 알아야 대비 가능 |
| 로그인 만료 | 한 AI의 로그인 갱신 열쇠가 11-26 06:36 만료 예정. 다른 AI는 짧은 출입증이 11-21 11:07에 만료됐으나 이후 호출은 성공 | 만료 전에 사람이 다시 로그인해야 함 |
| 계정 공유 | 방(팀)은 서로 독립인데 결제·로그인 계정은 **여러 방이 공유**. 한 방이 한도를 쓰면 다른 방 AI도 멈출 수 있음(점검보고서 11-21의 최대 약점) | 한 곳의 사용량이 다른 곳을 막음 |
| 지침 변조·자체 수정 | 팀장 AI가 스스로 스킬(기능 설명서)을 고치는 일이 가능 | 해시로 바뀐 것을 즉시 발견 |
| 게이트웨이 중복 | 같은 봇을 두 프로그램이 받으면 오동작 | 충돌 항목으로 확인 |
| 폰 서버 특성 | 폰은 와이파이·방전·재부팅에 약함. 11-22에는 방전으로 폰이 꺼진 일이 있었음 | 폰 상태를 따로 봄 |

서버 사양 자체는 병목이 아니었습니다(11-21 실측: 부하 0.03, 가용 메모리 약 5.4GB). 진짜 병목은 **계정(한도·크레딧·로그인)** 입니다. 그래서 점검의 절반은 "돈과 로그인"입니다.

### 2-2. 서버 자동 점검 항목 (Claude가 읽어서 판정)

| 항목 | 보는 법 | 정상 기준 | 이상할 때 |
| --- | --- | --- | --- |

| 핵심 스킬 2종 | 지난 점검과 내용 비교 | 같음 | 바뀌었으면 차이를 보고. 독립성·호출 제한 규칙이 약해졌으면 사람이 결정 |

도구 17개는 "초보자가 도구 동작을 보며 배우게 하려는" 사용자 결정(11-21)에 따른 기준입니다. 운영 방침이 바뀌면 이 기준도 같이 바꿉니다.

### 2-3. 충돌 여부 (서로 부딪혀서 조용히 멈출 수 있는 것)

| 항목 | 기준 | 다르면 |
| --- | --- | --- |

| 켜진 게이트웨이 서비스 수 | 1 | 2 이상이면 같은 봇을 둘이 받는 중. 하나만 남김 |
| 텔레그램 겹침 오류(409) | 0 | 1 이상이면 같은 봇 토큰을 다른 곳에서도 쓰는 중 |
| 봇 토큰 잠금 수 | 1 | 0이면 게이트웨이 비정상, 2 이상이면 토큰 중복 |
| OpenAI 로그인 오류 | 0 | 1 이상이면 같은 계정을 나눠 쓰는 다른 환경과 충돌 가능 |

이 충돌 점검이 못 잡는 것: 지침과 스킬 사이의 **내용상 규칙 충돌**은 자동으로 못 잡습니다. 지침 해시가 바뀐 때 사람이 내용을 비교해야 합니다.

## 3. 판정 방법 (정상·주의·위험)

판정은 신호등으로 표시합니다. 항목마다 위 표의 기준이 있고, **가장 나쁜 항목 하나가 전체 판정**입니다.

| 판정 | 뜻 | 사람이 할 일 |
| --- | --- | --- |
| 🟢 정상 | 모든 항목이 기준 안 | 보고만 읽고 끝 |
| 🟡 주의 | 기준을 약간 벗어남, 아직 멈추지 않음 | 보고를 읽고 원인 확인을 요청. 며칠 지켜봄 |
| 🔴 위험 | 이미 멈췄거나 곧 멈출 가능성 큼, 또는 지침이 몰래 바뀜 | 그날 처리 |

**갱신 일정 판정(별도 규칙)**: 만료일이 14일 이내면 🟡, **3일 이내면 🔴** 로 표시하고 보고 맨 위에 둡니다.

**보고 순서(매번 같은 순서)**

1. 종합 신호등과 한 줄 요약
2. 갱신 일정(D-day)
3. 사용자 대기 항목(내가 결정·처리해야 할 일 목록)
4. 현황표(에이전트·프로필·봇 수)
5. 이상 항목만 번호·값·판정으로
6. 지난 점검 대비 바뀐 것(지침·스킬 해시)
7. 권장 조치 0~2개

**원인을 말할 때의 표현 규칙**: "확인됨"(직접 읽음), "추정"(짐작), "미확인"(알 수 없음) 중 하나를 붙입니다. 원인을 단정하지 않습니다.

## 4. 이상할 때 대처

**공통 순서**: ① 보고만 하고 서버를 바꾸지 않는다 → ② 원인을 "확인됨/추정/미확인"으로 나눈다 → ③ 바꿀 일이 있으면 **변경 전 사본과 해시를 남기고 사람이 승인한 뒤** 한다.

| 상황 | 순서 |
| --- | --- |
| 지침·스킬 해시가 달라짐 | 변경 전 사본과 내용을 비교해 보고 → 되돌릴지는 사람이 결정. 되돌리기는 사본을 원래 이름으로 복사한 뒤 텔레그램에서 `/new` |
| 로그인·한도 오류 | 오류 메시지에 한도 해제 시각이 있으면 알려 줌. GPT 계열은 사람이 `hermes auth add openai-codex`, Claude 계열은 `claude auth login`을 실행(비밀번호·코드는 사람이 직접 입력) |
| 게이트웨이 정지 | 로그 마지막 줄을 먼저 보여 줌. 재시작은 승인 후 `systemctl --user restart <게이트웨이_서비스_이름>` (11-20에는 종료 코드 1이 나와도 정상이었음) |
| 봇이 답하지 않음 | 아래 5단계 |
| 비용 초과 | 긴 대화는 `/new`로 끊기, 문맥 한도 낮추기, 자료 분석은 싼 모델로(적용은 승인 후) |
| 크레딧 곧 소멸 | 소멸 예정 금액은 써도 손해가 없으므로 큰 작업을 그 전에 몰아서 하고, 소멸 뒤 새 크레딧 입금일을 확인 |

**봇이 답하지 않을 때 (사용자 체크리스트의 5단계)**

1. `.1 안녕`을 **한 번만** 다시 보내고 1분 기다립니다. 연속으로 보내면 진행 중인 작업에 합쳐져 비용이 겹칩니다. 번호 코드는 마침표를 꼭 붙입니다.
2. Console에서 잔액·키 상태(크레딧 0, 한도 초과, 키 삭제)를 봅니다.
3. `/new`를 보내고 승인 버튼을 눌러 다시 시험합니다.
4. Claude에게 "일반협업팀 점검해줘"라고 말하고 결과를 전달합니다.
5. 그래도 안 되면 서버 재시작(폰 서버면 폰 재부팅)을 상의합니다. 명령은 Claude 안내를 따릅니다.

재시작 직후 첫 응답은 약 45초 걸릴 수 있으며 이상이 아닙니다.

**폰 서버의 와이파이·전원 문제 (실제 시험 기록)**

- 알려진 문제: 와이파이가 끊겼다 다시 붙으면 텔레그램이 안 살아나고 폰을 껐다 켜야 했다는 기록이 있었습니다(원인 미확인).
- 11-22 시험(직접 설치한 환경): 와이파이를 60초, 5분 끊었다 켜도 **재부팅 없이 스스로 복구**했고 5분 끊김은 켠 지 약 18초 만에 복구됐습니다.
- 11-22 폰 꺼짐은 와이파이가 아니라 **방전**이었고 벽 충전기로 교체했습니다.
- 11-24 유선 전환 시험: 랜선을 뽑았다 꽂으면 약 2분 안에 터널이 자동 재연결되고 텔레그램 수신이 복구됐으며 게이트웨이 재시작은 0이었습니다.
- 터널이 안 열리면: ① 서버 쪽 포트가 죽은 옛 연결에 잡혀 있는지 확인(약 90초 안에 스스로 정리되어야 함) → ② 랜 어댑터 연결과 충전 확인 요청 → ③ 폰을 서버 USB에 꽂아 점검 요청. 세션 종료·재시작은 먼저 보고하고 승인받습니다.

**절대 하지 말 것**

- 키·토큰·비밀번호를 채팅에 쓰거나 화면을 캡처해 보내기(봇 만들기 화면 포함)
- 답을 기다리는 동안 메시지를 연달아 보내기
- 키 이름이 비슷하다고 헷갈려 지우기(지금 쓰는 키가 비슷한 이름으로 여러 개 있음)
- 승인 없이 서버 설정 바꾸기
