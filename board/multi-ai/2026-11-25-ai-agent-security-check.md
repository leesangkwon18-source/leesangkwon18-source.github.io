# AI 에이전트(Hermes Agent) 설치 후 보안 점검·설정 매뉴얼 (비전문가용)

> **이 글이 말하는 것:** 한 사용자가 Windows 안에 리눅스(WSL)를 깔고 AI 에이전트 Hermes Agent(v0.22.2)를 설치한 뒤, 2026년 10월 23~26일에 보안을 점검하고 설정한 과정을 쉬운 말로 정리한 것입니다.
> **확인된 것:** 격리 장치(Docker)의 작동, 읽기 전용 폴더와 쓰기 폴더의 구분, 도구 권한 목록, 스킬 변경 승인 설정이 코드에서 켜진 것(값이 True로 읽힘)까지입니다.
> **확인하지 못한 것:** 실제로 AI가 움직이는 동안의 격리 상태, 파일을 고치거나 지울 때 사람 승인이 반드시 뜨는지, 승인 창이 실제로 뜨는 모습입니다. 그래서 결론은 "조건부로 사용 가능, 기존 파일을 AI가 자동으로 바꾸게 하는 일은 보류"입니다.

## 0. 먼저 읽기

### 이 글이 다루는 것
- AI 에이전트를 설치한 직후에 "AI가 내 파일을 마음대로 건드릴 수 있는가?"를 점검하는 순서
- 점검할 때 쓴 명령, 그 결과, 결과를 읽는 법
- 안전을 높이려고 바꾼 설정 2가지(폴더 구분, 스킬 승인)

### 이 글이 다루지 않는 것
- Hermes Agent 설치 방법 자체(별도 매뉴얼이 있습니다. 이 글의 자료에는 설치 절차가 없습니다)
- 텔레그램 연결, 서버(VPS)에서 늘 켜 두기: 자료에서 "미착수"였습니다
- 투자 판단 등 AI에게 시킬 업무의 내용
- 자료에 없는 일: 보안 점검에서 "완벽하다"는 보증

### 자리표시자(꺾쇠 <> 로 쓴 말)
이 글에는 `<내_계정>`, `<프로젝트_폴더>`처럼 꺾쇠로 쓴 말이 나옵니다. **자리표시자는 독자가 자기 값으로 바꾸는 자리**입니다. 실제 계정 이름, 폴더 이름은 사람마다 다르고 공개하면 안 되는 정보라서 일부러 바꿔 썼습니다. 명령을 따라 칠 때는 꺾쇠까지 지우고 자기 값을 넣으세요.

### 용어 풀이 (처음 나올 때도 한 번 더 풀어 둡니다)
| 용어 | 한 줄 풀이 |
|---|---|
| AI 에이전트 | 질문에 답만 하는 게 아니라, 명령을 실행하고 파일을 만드는 등 "일을 하는" AI 프로그램 |
| WSL | Windows 안에서 리눅스(여기서는 Ubuntu)를 함께 돌리는 기능 |
| PowerShell | Windows에서 글자로 명령을 내리는 창 |
| Docker | 프로그램을 "작은 방(컨테이너)" 안에 가둬서 돌리는 도구. 방 밖의 파일은 기본적으로 못 봅니다 |
| Rootless Docker | 관리자 권한 없이 도는 Docker. 방이 뚫려도 피해가 작도록 하는 방식 |
| 마운트 | 내 PC의 폴더를 작은 방 안에 "문"처럼 연결하는 것 |
| ro / rw | read-only(읽기만 가능) / read-write(읽기·쓰기 가능) |
| 승인(approval) | AI가 위험한 명령을 하기 전에 사람에게 "해도 됩니까?" 묻는 절차 |
| 스킬 | AI가 배워 두는 작업 요령 묶음. AI가 스스로 만들거나 고칠 수도 있음 |
| 부하 AI(서브에이전트) | 주 AI가 일을 나눠 맡기려고 만드는 보조 AI |
| SHA-256 | 파일 내용이 같은지 비교하는 "지문" 값 |
| dry-run | 실제로 하지 않고 "이렇게 할 것이다"만 보여 주는 연습 실행 |

| 항목 | 값 |
|---|---|
| 바탕 | Windows + PowerShell, 안쪽에 WSL Ubuntu 24.04.4 LTS |
| 격리 | Docker Engine 29.9.2 (Rootless) |
| AI 에이전트 | Hermes Agent v0.22.2 |
| 파이썬 | 3.14.8 (Hermes 전용 가상환경 사용) |

| 보조 AI | GPT 계열 (OpenAI Codex 로그인만 확인됨) |
| Hermes 설치 위치 | `/home/<내_계정>/hermes-agent` |
| Hermes 설정 파일 | `/home/<내_계정>/.hermes/config.yaml` |
| Windows 쪽 프로젝트 | `<프로젝트_폴더>` (D: 드라이브 안에 있음) |

### 1-2. 점검 규칙 (이 규칙대로 했습니다)
1. **읽기 전용 검사부터** 합니다. 파일을 바꾸는 일은 사용자 승인 후에만 합니다.
2. 기존 Windows 파일은 수정·삭제·이동·이름 변경을 하지 않습니다.
3. Windows 프로젝트 폴더를 Docker 방에 **직접** 연결하지 않습니다.
4. PowerShell 명령은 **한 번에 하나씩** 실행하고, 결과를 본 뒤 다음으로 갑니다. (초보자는 여러 줄을 한꺼번에 붙이면 어디서 틀렸는지 알 수 없습니다.)
5. 확인한 것과 추정·미확인을 구분해서 적습니다.

### 1-3. 명령을 치는 모양
Windows PowerShell에서 리눅스 명령을 실행할 때는 앞에 `wsl -d Ubuntu --`를 붙입니다. 예:

```powershell
wsl -d Ubuntu -- ls /home/<내_계정>/.hermes
```

## 2. 점검 1단계: 격리 방(Docker)이 제대로 작동하는가

### 왜 하는가
AI 에이전트는 명령을 실행합니다. 그 명령이 내 PC 전체에 닿지 않도록 "작은 방"에 가두는 것이 첫 번째 방어선입니다. 방이 실제로 닫혀 있는지부터 봐야 합니다.

### 무엇을 했는가
Hermes가 쓰는 방과는 **별도로**, 점검용 임시 방을 하나 만들었습니다. 이 방은 다음 조건으로 실행했습니다.
- `--rm`: 끝나면 자동으로 사라짐
- `--network none`: 인터넷 차단
- `--read-only`: 방 자체를 읽기 전용으로
- `/workspace` 폴더만 읽기 전용(ro)으로 연결

### 확인된 결과
- Rootless Docker가 정상 작동했습니다.
- 임시 방 안에는 `/workspace`가 있었고, Windows 드라이브(`/mnt/c`, `/mnt/d`)와 리눅스 홈 폴더(`/home/<내_계정>`)는 **보이지 않았습니다.**
- 마운트 정보에 `/workspace`가 `ro`(읽기 전용)로 나왔습니다.

### 주의: 이 결과의 한계
이것은 **점검용 임시 방**의 결과입니다. 실제 Hermes가 만드는 방이 똑같다는 증거가 아닙니다. 자료는 이 점을 여러 번 강조합니다. 실제 Hermes 방의 마운트와 Windows C:/D: 접근 여부는 이 단계에서 **미검증**이었습니다.

## 3. 점검 2단계: Hermes 설정 파일 읽기

### 왜 하는가
"실제 Hermes가 어떤 방을 어떻게 만들도록 설정되어 있나"는 설정 파일에 적혀 있습니다. 읽기만 하면 되므로 위험이 없습니다.

### 처음 확인된 설정 (10월 23일)
```yaml
terminal:
  backend: docker
  docker_network: false
  container_persistent: false
  cwd: /workspace
  docker_volumes:
    - /home/<내_계정>/hermes-work-staging:/workspace:rw
  degraded_mode: error
  docker_mount_cwd_to_workspace: false
```

### 쉬운 풀이
| 설정 | 뜻 |
|---|---|
| `backend: docker` | 명령을 Docker 방 안에서 실행 |
| `docker_network: false` | 방의 네트워크 차단 설정 |
| `container_persistent: false` | 방을 매번 새로 만들고 지움(흔적이 남지 않음) |
| `docker_volumes ... :rw` | 리눅스 쪽 임시 폴더 하나를 방 안 `/workspace`에 읽기·쓰기로 연결 |
| `degraded_mode: error` | Docker를 못 쓰게 되면 조용히 다른 방식으로 바꾸지 말고 오류를 내라 |
| `docker_mount_cwd_to_workspace: false` | 지금 있는 폴더를 자동으로 방에 연결하지 않음 |

### 확인된 점과 걸린 점
- 확인됨: Windows `D:` 프로젝트 폴더는 연결 목록에 **없습니다.**
- 걸린 점: 실제 Hermes의 `/workspace`는 `rw`(쓰기 가능)입니다. 2단계의 점검용 방(`ro`)과 다릅니다. 즉 이 임시 폴더 안의 파일은 AI가 고칠 수 있습니다.

## 4. 점검 3단계: 위험한 명령을 사람에게 물어보는가 (승인 장치)

### 왜 하는가
방이 닫혀 있어도, 방 안에 연결된 폴더의 파일은 AI가 지울 수 있습니다. 그래서 "지우기 전에 사람에게 묻는가"가 두 번째 방어선입니다.

### 무엇을 했는가
1. **소스 코드 읽기:** 승인 검사 함수(`check_all_command_guards`, `tools/approval.py` 1128행 부근)를 읽기 전용 명령(`grep`, `sed`)으로 찾아 읽었습니다.
2. **판정 시험:** 실제로 지우지 않고 "이 삭제 명령을 허용하겠는가"만 물어보는 시험을 했습니다.

```text
hermes approvals test --env-type docker -- rm -f /workspace/기존파일.txt
verdict: allow
```

3. **설정 검색:** 설정 파일에서 `approvals:` 항목을 찾았지만 **출력이 없었습니다.**

### 확인된 결과
- 코드에는 승인을 건너뛰는 길이 여러 개 있었습니다. 승인 기능을 끄는 모드(YOLO 또는 `approvals.mode=off`), 영구 허용 목록, 위험하지 않다고 판단된 명령, 이미 승인된 유형 등입니다.
- 삭제 명령 시험의 판정은 `allow`(허용)였습니다. 이것은 **시험**일 뿐 실제 삭제는 없었습니다. 왜 허용으로 나왔는지는 끝내 **완전히 밝히지 못했습니다.**
- `approvals:` 검색에 결과가 없다는 것은 "그런 모양의 항목을 못 찾았다"는 뜻이지, 승인 모드가 꺼져 있다는 뜻이 아닙니다.

### 결론 (10월 23일)
"모든 파일 변경 전에 사람이 승인한다"고 믿을 근거는 **확보되지 않았습니다.**

## 5. 점검 4단계: 코드를 더 깊이 읽기 (10월 24일 최종 보고)

### 왜 하는가
3단계에서 풀리지 않은 의문(승인이 왜 `allow`인가, 우회 길이 있는가)을 소스 코드를 읽어 좁히기 위해서입니다. 이 단계도 모두 읽기 전용입니다.

### 확인된 내용
| 파일 | 알게 된 것 |
|---|---|
| `tools/approval_context.py` | 승인 모드는 설정이 없으면 기본 `manual`(수동)로 취급됨. 다만 실행 상황에 따라 정책이 바뀔 가능성이 있음 |
| `tools/terminal_tool.py` | 명령 실행 전에 승인 검사 함수를 부르지만, `force=True`이면 일반 승인 검사를 통과시키는 코드가 있음 |
| `agent/terminal_approval_batch.py` | 승인 결과는 한 번만 쓰이고, 앞선 명령이 실패하면 기존 결정이 버려지며, 명령 인수가 바뀌면 오류가 나도록 되어 있음(좋은 장치) |
| `tools/approval.py` | 승인을 건너뛰는 여러 길이 있어서 `manual`이라는 말이 "모든 파일 변경마다 사람이 승인"을 뜻하지 않음 |
| `execute_code` 관련 주석 | 임의의 코드 실행이 터미널 승인 길을 우회해 파일을 바꿀 수 있다는 설계상 한계가 적혀 있음. 단 그 시점 설정에서는 `code_execution` 도구가 꺼져 있었음 |

### 풀리지 않은 의문
- AI가 직접 `force`를 켤 수 있는가: **미확인.** (`force` 검색에서 나온 것은 플러그인·대화 압축 관련이었고, 이 검색만으로는 증명도 부정도 못 합니다.)
- 시험의 `allow` 판정이 실제 실행 환경과 같은가: **미확인.**

### 최종 판정 (10월 24일)
> **조건부 위험.** Hermes의 기본 승인 기능만으로 기존 파일 수정·삭제에 대한 사전 승인을 보장할 수 없다.

자료는 이것이 "실제로 공격당했다"는 뜻이 아니라, 확인된 자동 승인·우회 길과 쓰기 권한에 근거한 **보호 수준 평가**라고 덧붙입니다.

## 6. 점검 5단계: 읽기 전용 폴더와 쓰기 폴더를 나누기 (10월 25~26일)

### 왜 하는가
"AI의 눈치나 위험 명령 탐지"에만 기대지 말고, **운영체제와 Docker가 물리적으로 막아 주는** 구조를 만드는 것이 가장 믿을 만하기 때문입니다. 자료의 권장안도 이것이었습니다: 기존 자료는 읽기 전용으로, AI가 새로 만들 결과물만 별도 쓰기 폴더로.

### 무엇을 했는가
설정 파일의 `terminal` 부분을 다음처럼 바꿨습니다. 바꾸기 전 설정 파일은 백업했습니다(백업 이름에 보안 작업 전이라는 뜻의 날짜 표시를 붙임).

```yaml
terminal:
  backend: docker
  docker_network: false
  container_persistent: false
  cwd: /workspace/output
  docker_volumes:
    - /home/<내_계정>/hermes-work-staging:/workspace/reference:ro
    - /home/<내_계정>/hermes-output:/workspace/output:rw
  docker_run_as_host_user: false
  degraded_mode: error
  docker_mount_cwd_to_workspace: false
```

| 방 안 위치 | 연결된 폴더 | 권한 | 역할 |
|---|---|---|---|
| `/workspace/reference` | 참조 자료 폴더 | `ro` | 읽기만 가능 |
| `/workspace/output` | 결과물 폴더 | `rw` | AI가 만든 결과를 둠 |

`docker_run_as_host_user: false`는 Rootless Docker에서 사용자 번호 대응 때문에 결과 폴더 쓰기가 막히는 문제를 풀려고 조정한 값입니다(자료 설명: "출력 폴더 쓰기 시험을 통과하도록 조정").

### 확인된 시험 결과
| 시험 | 결과 |
|---|---|
| Rootless Docker 보안 옵션 | 확인 |
| 참조 폴더가 읽기 전용으로 연결됨 | 확인 |
| 참조 폴더에 파일 쓰기 시도 | **차단됨**, 시험 파일이 생기지 않음 |
| 결과물 폴더에 파일 쓰기 시도 | 성공 |
| 네트워크 차단(`--network=none`) | 소스 코드에서 인자 구성만 확인(실제 방에서 통신 시험은 한 기록 없음) |
| 모든 Hermes 도구가 Docker 안에서만 도는가 | **미검증** |

### 한계 (중요)
Docker의 읽기 전용 보호는 **그 방 안에서만** 적용됩니다. 다른 도구가 방을 거치지 않고 WSL·Windows 파일에 직접 닿는 길까지 자동으로 막아 주지는 않습니다.

## 7. 점검 6단계: 건강검진(doctor)과 상태 확인

### 왜 하는가
설치가 온전한지, 어떤 키와 로그인이 등록됐는지 보면 "의도하지 않은 연결"을 찾을 수 있습니다.

### 확인된 결과 (읽기 전용 진단)
- 정상: 파이썬, SQLite, 필수 패키지, 인증서 저장소, Docker 데몬, 설정 파일 버전, Anthropic 설정, OpenAI Codex 로그인

- 선택 기능 경고: 텔레그램·디스코드 라이브러리, ripgrep, Node.js, 브라우저 도구 등

## 8. 점검 7단계: AI에게 허용된 도구 확인

### 왜 하는가
AI가 쓸 수 있는 도구가 적을수록 사고 범위가 줄어듭니다.

### 확인된 결과 (`hermes tools --summary`)
27개 그룹 중 9개가 켜져 있었습니다.

- **켜짐:** 웹, 비전(그림 읽기), 이미지 생성, 음성 합성, 할 일, 기억, 세션 검색, 되묻기, 위임(부하 AI 만들기)
- **꺼짐(주요):** 터미널, 파일, 코드 실행, 컴퓨터 조작, 브라우저, 예약 작업, 스킬, 연결

이것은 **확인한 시점의 CLI 설정**이며, 다른 플랫폼·프로필·앞으로의 세션에도 같다는 보장은 없습니다.

### 첫 대화 시험
도구를 쓰지 말고 짧게 인사만 하라고 시켰고, "정상 작동 중"이라는 답을 받았습니다. 메시지 2개, 도구 호출 0회, `/exit`로 정상 종료했습니다. 즉 **연결과 답변은 확인**, 도구를 쓰는 작업은 시험하지 않았습니다.

## 9. 점검 8단계: 부하 AI는 주 AI보다 더 많은 권한을 갖지 않는가

### 왜 하는가
주 AI의 도구를 줄여 놓아도, 부하 AI가 더 센 권한을 얻으면 소용이 없기 때문입니다.

### 무엇을 했는가
부하 AI 생성 관련 소스 두 개(`delegate_tool_toolsets.py`, `delegate_tool.py`)를 읽었습니다.

### 확인된 점 (코드상)
- 부하 AI의 도구는 **주 AI의 도구를 기준으로** 계산됩니다. 주 AI에 없는 도구를 새로 주지 않도록 설계됨.
- `delegate_task`, `clarify`, `memory`, `send_message`, `cronjob_manage` 같은 일부 도구는 부하 AI에게 막혀 있음.
- `orchestrator`(조정자) 역할에는 위임 관련 예외가 있음.

### 한계
계산 결과가 실제로 만들어진 부하 AI에게 그대로 전달되는지, 우회 길이 없는지는 **실행해 본 적이 없습니다(미검증).**

## 10. 설정 단계: 스킬 변경에 승인 걸기 (10월 26일)

### 왜 하는가
Hermes는 백그라운드에서 스스로 스킬(작업 요령)을 만들거나 고치자고 제안할 수 있습니다. 자동 검토는 유용하니 **유지하되**, 스킬이 만들어지거나 바뀔 때는 사람이 승인하게 하려는 것입니다.

### 먼저 조사한 것 (읽기 전용)
- 코드에서 스킬 생성 제안 간격 기본값 10은 **분이 아니라 도구 반복 횟수** 기준입니다.
- `skills.write_approval`의 기본값은 `false`입니다. `true`로 하면 지원되는 스킬 변경이 승인 대기로 들어갑니다. (승인 대기 위치는 코드상 `/home/<내_계정>/.hermes/pending/skills/`)
- AI가 스스로 만든 스킬 목록을 조회하니 `[]`(비어 있음). 다만 과거에 만들었다가 지운 일까지 증명하는 것은 아닙니다.
- 수정 기록 파일(`.usage.json`)은 없어서 과거 수정 횟수는 알 수 없습니다. "자동 수정이 없었다"고 단정할 수 없습니다.

### 바꾸기 전 상태
- 백그라운드 검토: 켜짐
- 설정 파일에 `skills:` 항목 없음
- 승인 설정 값: **False**

### 실제로 한 일 (사용자 승인 후)
1. **백업:** 설정 파일을 복사해 `config.yaml.before_skill_approval`을 만들었습니다. 두 파일의 존재와 크기(약 1.2K)는 확인했지만, 내용이 같은지(SHA-256 비교)는 하지 않았습니다.
2. **기존 항목 확인:** `skills:` 항목이 없음을 확인.
3. **설정 추가:** 파일을 덮어쓰지 않고 맨 끝에 덧붙였습니다.

```powershell
wsl -d Ubuntu -- bash -lc 'printf "\nskills:\n  write_approval: true\n" >> /home/<내_계정>/.hermes/config.yaml'
```

추가된 내용:
```yaml
skills:
  write_approval: true
```

`>>`는 덧붙이기, `>`는 덮어쓰기입니다. 설정 파일에는 반드시 `>>`를 쓰세요. `>`를 쓰면 기존 설정이 사라집니다.

### 확인된 결과
```text
True
```
Hermes 코드가 이 설정을 "켜짐"으로 읽는다는 것까지 확인했습니다.

### 이 설정이 막아 주는 것과 못 막는 것
- 막아 줌: 스킬 관리 도구(`skill_manage`)를 통한 스킬 생성·수정
- **못 막음:** 터미널 명령이나 다른 파일 쓰기 도구로 파일을 바꾸는 일. 전역 파일 보호 기능이 **아닙니다.**
- `skills.guard_agent_created` 같은 별도 검사 기능과는 다른 것입니다(승인과 구분).
- D: 드라이브 지식창고의 읽기 전용 보호나 Windows 권한은 이 작업에서 바꾸지 않았습니다.

### 아직 못 한 것
- Hermes를 재시작해 설정이 실행 중인 프로그램에 반영됐는지: **미확인**
- 승인 대기·승인·거부가 실제로 뜨는지 시험: **미실시** (시험할 때는 기존 스킬이나 지식창고를 대상으로 쓰지 말 것)
- 재시작할 때는 진행 중인 작업이 있는지 보고, 정상 종료 후 다시 켭니다. 강제 종료하지 않습니다.

## 13. 앞으로 지킬 운영 원칙 (자료의 권장안, 구현 완료가 아님)

자료는 아래 흐름을 **권장 설계**로 제시합니다. 모든 단계가 이미 기술로 구현됐다는 뜻이 아닙니다.

```text
사용자 요청
   ↓
Hermes Agent
   ↓
Docker 격리 환경 (참조는 읽기 전용, 결과물만 쓰기)
   ↓
결과물 폴더에 저장
   ↓
파일 내용·경로·기존 파일과 비교
   ↓
사용자 승인
   ↓
Windows 프로젝트로 별도 반입
```

1. 기존 자료는 읽기 전용으로 연결하고, AI의 쓰기는 결과물 폴더에만 허용한다.
2. 실제 실행 직전에 마운트·권한·켜진 도구·승인 정책을 다시 확인한다.
3. "AI에게 부탁하는 말"이나 위험 명령 탐지를 마지막 방벽으로 믿지 않는다.
4. 기존 파일을 바꿔야 하면 사람이 대상과 내용을 확인한 뒤 따로 승인하고 진행한다.
5. 설정 변경 전에는 파일을 백업하고, 자동 수정 명령은 설명 없이 실행하지 않는다.
6. 터미널·파일·코드 실행 도구는 필요할 때만, 사용자 승인을 받아 제한적으로 켠다.

## 14. 한 줄 정리

**Hermes는 "조건부로 쓸 수 있다": 격리 방, 읽기 전용 참조 폴더, 꺼 둔 위험 도구, 스킬 승인으로 1차 방어는 세웠지만, 실제 실행 중의 격리와 파일 변경 승인은 아직 증명되지 않았으니 기존 파일을 AI가 자동으로 바꾸게 하지 마세요.**
