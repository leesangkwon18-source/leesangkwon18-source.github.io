> 이 문서는 Ubuntu 서버와 안드로이드 폰(Termux) 위의 Hermes Agent 환경을 **백업하고 검증하고 보관한 2026년 11월 1일~15일 기록**을 초보자용으로 정리한 것입니다. 가장 중요한 사실을 먼저 말씀드립니다.
>
> **이 기록에서 백업 파일은 여러 개 만들고 해시로 검증했지만, 백업으로 실제 복원해 본 적은 한 번도 없습니다.** 그래서 이 문서의 복원 절차는 **계획과 검토용 예시**이며, 복원 성공을 보증하지 않습니다. 확인된 것과 확인하지 못한 것을 구분해 적었고, 서버 주소·계정·키·해시 값 같은 개인 정보는 `<…>` 자리표시자로 바꾸거나 싣지 않았습니다.

## 0. 먼저 읽기

### 0.1 이 매뉴얼이 다루는 것

- 무엇을 백업해야 하는지, 백업의 **두 가지 수준**(작업 환경 복원점 / 시스템 이미지)
- 서버용(암호화·비암호화), 폰용, 팀별(다른 계정) 백업 **만드는 방법**
- 백업이 **믿을 만한지 확인하는 단계**(검증 사다리)
- PC에 **이중 보관**하는 법과 해시 대조
- 흔한 **함정**과 실제로 겪은 문제
- 백업 **보관·정리 원칙**
- **복원 계획**(실행하지 않은 절차)과 복원 후 점검표

### 0.2 이 매뉴얼이 다루지 않는 것

- Hermes 설치 자체 → 설치·운영 매뉴얼
- 협업 규칙 → 「AI 협업 운영 매뉴얼」
- OS 전체 디스크 이미지 만드는 법 → 기록에 실제 수행 사례가 없음(2.2)

### 0.3 자리표시자

| 자리표시자 | 의미 |
| --- | --- |
| `<서버_주소>`, `<서버_계정>`, `<서버접속_키>` | 서버 접속 정보(비공개) |
| `<서버_홈>` | 서버 계정 홈 폴더 |
| `<백업_폴더>` | 백업을 모아 두는 폴더 |
| `<백업이름>` | 날짜·차수가 들어간 백업 파일 이름 |
| `<PC_백업_경로>` | 메인 PC의 백업 보관 경로 |
| `<64자리_해시값>` | SHA-256 값 |
| `<날짜>` | 예: 20261103 형식 |

### 0.4 명령을 어디서 치는가

| 표시 | 뜻 |
| --- | --- |
| **메인 PC PowerShell** | Windows PC의 PowerShell |
| **서버 Ubuntu 터미널** | 서버에 로그인한 뒤의 셸 |
| **폰 Termux** | 안드로이드 폰의 Termux 앱 |
| **Hermes 대화창** | AI에게 말하는 창. **셸 명령을 여기 넣지 않습니다** |

> 실제로 서버 셸에 PowerShell 명령(`Test-Path`)을 쳐서 구문 오류가 난 적이 있습니다. 백업에는 영향이 없었지만, 명령 전에 **"지금 어느 장비인가"**를 확인하세요. 명령은 **한 번에 하나씩** 실행하고 출력을 확인한 뒤 다음으로 갑니다.

## 1. 핵심 원칙

1. **복원 가능성이 목적이다.** 파일을 복사했다고 백업이 끝난 것이 아닙니다. 범위, 누락, 복원 순서, 무결성, 복원 시험을 기록합니다.
2. **정상 작동 중인 서버를 건드리지 않는다.** 백업 때문에 소스 수정, 패키지 업데이트, 재로그인, 서비스 재시작, 파일 삭제를 하지 않습니다.
3. **읽기 전용 조사 → 범위·보관처·민감정보 합의 → 승인 → 복사 → 해시 검증 → 복구 문서 → (가능하면) 별도 환경 복원 시험.**
4. **기존 백업은 보존한다.** 덮어쓰지 않고 날짜·차수별 새 폴더/새 이름을 씁니다. 같은 이름의 파일이 있으면 **중단**하도록 만듭니다(4.1).
5. **비밀값은 특별 취급한다.** `.env`, 인증 파일, OAuth 토큰, 봇 토큰, SSH 개인키의 **내용을 출력·채팅·문서에 싣지 않습니다.** 백업 파일에는 그것들이 **들어 있을 수 있습니다**(9장).
6. **복원은 백업보다 위험하다.** 장애가 나기 전에는 **운영 중인 서버에 복원 시험을 하지 않습니다.**
7. **불필요한 추가 과금 금지.** 백업 때문에 유료 API를 켜지 않습니다.
8. **"백업 및 무결성 검증 완료, 복원 시험 미실시"라고 정확히 말한다.** 이것이 지금까지 기록의 정직한 상태입니다.

## 2. 무엇을 어느 수준까지 백업할까

### 2.1 수준 ① — Hermes 작업 환경 복원점 (이 기록의 방식)

Windows의 "복원 지점"과 비슷하게, **지금 잘 되는 Hermes 환경을 되돌릴 수 있게** 보관합니다. 기능이 엉켰을 때 비교하거나 일부만 되살리는 데 적합합니다.

| 포함 대상 | 설명 |
| --- | --- |
| Hermes 홈(`.hermes`) | 설정, 스킬, 세션·기억, 예약 작업, 원장 |
| 사용자 서비스 정의 | Gateway를 띄우는 systemd 사용자 서비스 파일 |
| 실행 파일·프로그램 | Hermes 실행 명령, Claude·Codex 설치 파일 |
| 인증·설정 폴더 | `.claude`, `.codex`, `.config`, `.ssh` 등 |
| SQLite DB | **온라인 백업 방식으로 따로**(4.3) |

### 2.2 수준 ② — 서버 전체 시스템 이미지 (기록에 수행 사례 없음)

- SSD 고장이나 OS 손상에 대비하는 방식입니다. 디스크 구조·부팅 파티션·암호화 여부·목적지 용량·도구·서비스 중단 필요성을 **먼저 확인**한 뒤 **별도 승인**으로 계획해야 합니다.
- **운영 중인 파일시스템을 그냥 통째로 복사한 것은 부팅 가능한 이미지가 아닙니다.**
- 이 기록의 백업은 모두 수준 ①입니다. **OS 패키지, 커널, 시스템 전역 서비스, 외부 경로는 포함되지 않습니다.**

### 2.3 백업이 포함하지 못하는 것 (항상 확인)

| 포함 못 하는 것 | 이유 / 대응 |
| --- | --- |
| Android OS, 앱 설치(APK), 앱 권한, 배터리 예외, USB 디버깅 승인 | 폰 tar 백업 범위 밖. **별도로 준비** |
| **프로세스 메모리에만 있던 자료**(예: 메모리에서 돌던 데이터 서비스) | 파일 백업에 없음. 복원 후 수동 재준비가 필요 |
| 계정 밖 심볼릭 링크 대상 | 링크만 보존되고 대상 파일은 안 들어갈 수 있음 |
| OAuth·로그인 유효성 | 파일이 있어도 **만료되었을 수 있음** → 재로그인이 필요할 수 있음 |

## 3. 시작 전 점검 (읽기 전용)

1. 대상 폴더의 **존재·크기·권한**만 먼저 확인(`du -sh`, `ls -ld`).
2. 백업 목적지의 **여유 공간** 확인(`df -h`). 기록 당시 서버 디스크는 수백 GB 중 20~30GB 사용 상태였습니다.
3. 기존 백업 목록을 확인하고 **이번 파일 이름이 겹치지 않는지** 확인.
4. 캐시 폴더(예: 패키지 캐시)처럼 **다시 만들 수 있는 것은 제외**할 후보로 분류.
5. 소켓 파일(`*.sock`)은 백업할 수 없으므로 제외.
6. 비밀값이 든 파일은 **내용을 열지 말고** 경로·권한만 확인(`600` 여부).

```bash
# 서버 Ubuntu — 용량·권한 확인 예 (내용은 열지 않음)
du -sh <서버_홈>/.hermes <서버_홈>/.claude <서버_홈>/.codex 2>/dev/null
ls -ld <서버_홈>/.hermes <서버_홈>/.ssh
df -h <서버_홈>
```

## 4. 서버 백업 만들기

### 4.1 방식 A — 암호화 백업 (레거시 4차에서 실제 사용)

`tar`로 묶은 뒤 **파이프로 GPG에 바로 넘겨 암호화**합니다. 중간에 암호화 안 된 압축 파일이 디스크에 남지 않습니다.

```bash
# 서버 Ubuntu (GPG가 터미널에서 암호를 물을 수 있게 먼저 설정)
export GPG_TTY="$(tty)"; gpg-connect-agent updatestartuptty /bye
```

```bash
(
  umask 077
  set -o pipefail
  OUT="$HOME/<백업_폴더>/<백업이름>.tar.gz.gpg"
  if [ -e "$OUT" ]; then echo "중단: 같은 이름의 백업이 이미 있음"; exit 1; fi
  tar -C "$HOME" \
    --exclude='.hermes/cron/*.db' --exclude='.hermes/cron/*.db-wal' \
    --exclude='.hermes/cron/*.db-shm' --exclude='*.sock' \
    -czf - .hermes .config .local .claude .codex .ssh <DB_온라인백업_폴더> \
  | gpg --no-symkey-cache --symmetric --cipher-algo AES256 --output "$OUT"
  echo "종료 코드: ${PIPESTATUS[*]}"
)
```

- `umask 077` → 만들어지는 파일은 소유자만 읽고 씀
- **같은 이름이 있으면 중단**(덮어쓰기 방지)
- `종료 코드 A B`에서 A는 `tar`, B는 `gpg`입니다. **둘 다 0이어야** 깨끗합니다.
- 비밀번호는 **본인이 직접 입력**하고 채팅·문서에 쓰지 않습니다. **백업 파일과 비밀번호를 같은 곳에 두지 않습니다.**
- 이 기록의 4차 백업은 약 1.5GB였습니다(수 GB의 `.hermes`에서 캐시 제외).

### 4.2 방식 B — 비암호화 백업 + 권한 제한 (일반협업팀·다른 팀 계정에서 사용)

```bash
(umask 077; tar -czf <서버_홈>/<백업_폴더>/<백업이름>.tar.gz -C <서버_홈> <대상_폴더> <서비스_파일_상대경로>)
```

- 파일 권한 **600**, 폴더 **700**으로 접근을 제한했습니다.
- **암호화되어 있지 않습니다.** 토큰·OAuth·대화 기록이 들어 있을 수 있으므로 외부 공유 금지(9장).
- 이 방식은 간편하지만, **PC로 옮기거나 외부 저장소에 둘 때는 암호화를 고려**하는 것이 안전합니다(작성자 권장, 12.3).

### 4.3 SQLite DB는 따로 "온라인 백업"

쓰는 중인 DB 파일을 그냥 복사하면 **복원이 안 되는 파일**이 될 수 있습니다. Python의 `sqlite3.Connection.backup`을 써서 **별도 복사본**을 만들고, 그 복사본을 백업에 포함합니다.

```python
# 서버에서 (개념 예시) — 원본 DB는 읽기만, 복사본은 새 폴더에
import sqlite3
src = sqlite3.connect("file:<원본.db>?mode=ro", uri=True)
dst = sqlite3.connect("<복사본.db>")
src.backup(dst); dst.close(); src.close()
```

- 복사본마다 `PRAGMA integrity_check`로 **`ok`** 인지 확인했습니다.
- 한계: DB를 **차례로** 복사했으므로 DB들이 **같은 한 시점이라는 보장은 없습니다.**
- 운영 중 DB(`*.db`, `*.db-wal`, `*.db-shm`)는 tar 대상에서 **제외**하고, 복사본만 백업에 넣었습니다. 그래서 **복원 때는 복사본을 운영 경로로 직접 옮겨 배치하는 단계가 따로 필요**합니다.
- **주의:** 이 복사본 폴더는 암호화된 백업 안에도 있지만 **서버 디스크에 암호화되지 않은 채** 남을 수 있습니다. 백업 검증 후 정리 여부를 승인받아 결정하세요.

### 4.4 방식 C — 폰(Termux) 백업

- 대상: Termux의 `home`과 `usr`(PRoot Ubuntu의 루트 파일시스템 포함)을 `.tar.gz`로 묶음(약 6.6GB, 항목 약 29만 개).
- **제외한 것**: 백업 파일 자기 자신, PRoot 안의 Android 시스템·가상 마운트 경로(`dev`, `proc`, `sys`, `sdcard` 등), 서비스 감시 상태 폴더, 임시 실행 경로.
- 확인된 포함 파일 예: Termux 부팅 스크립트, Gateway 실행 스크립트, PRoot 안의 `.hermes` 설정.
- **이 백업은 폰 전체 이미지가 아닙니다.**(2.3)
- 폰의 저장 공간이 모자라면 큰 백업은 **서버·PC로 전송하는 경로**를 함께 설계해야 합니다. 전송이 끊기면 **작은 잔재 파일**이 남을 수 있습니다(8장).

### 4.5 방식 D — 다른 팀(다른 Linux 계정) 백업

- 별도 계정(예: 전문 팀)은 **그 계정 홈 전체 + 서비스 파일 + 계정 설정(linger 등)**을 대상으로 백업했습니다. 관리자 권한이 필요한 부분은 **사용자가 직접** 비밀번호를 입력해 진행합니다(AI가 비밀번호를 입력하지 않습니다).
- 기록된 크기 약 4.0GB, 항목 약 9.8만 개, 소요 약 7분, 종료 코드 0.
- **계정 번호(UID/GID)·홈·셸 정보**를 상태 파일에 함께 기록해 두면 복원 때 비교할 수 있습니다.
- 다른 팀의 백업을 만들 때 **다른 팀의 계정·서비스·파일은 건드리지 않습니다.**

### 4.6 변경 경고: `file changed as we read it`

실행 중인 환경을 백업하면 `tar`가 "읽는 도중 파일이 바뀌었다"고 경고하고 **종료 코드 1**을 낼 수 있습니다.

- 레거시 4차 백업(종료 코드 `1 0`)과 폰 백업에서 실제로 나왔고, **원인 파일이 로그·상태 파일이었어도 일관된 스냅샷이라는 보장은 없습니다.**
- 줄이는 방법: 백업 중 **변경 작업을 중단**하고, 승인을 받아 **해당 서비스만 잠시 정지**한 뒤 백업(일반협업팀 2차 백업에서 사용). 정지하면 서비스가 잠시 중단되므로 시간을 정하세요.
- 로그·상태 파일처럼 변동이 큰 것의 처리는 **다음 백업에서 개선할 과제**로 남겼습니다.

## 5. 검증 사다리 — 백업이 "믿을 만한가"

아래 단계는 **위로 갈수록 더 강한 증거**입니다. 해시·압축 검사 통과는 **복원 성공의 증거가 아닙니다.**

| 단계 | 방법 | 알 수 있는 것 | 모르는 것 |
| --- | --- | --- | --- |
| 1 | 종료 코드 확인 | 도구가 오류 없이 끝났는가 | 내용이 완전한가 |
| 2 | `gzip -t` | 압축 스트림이 깨지지 않았는가 | 내용이 맞는가 |
| 3 | `tar -tzf … > /dev/null` | 목록 전체를 읽을 수 있는가 | 파일 내용 |
| 4 | **핵심 경로 포함 확인** | 꼭 필요한 파일·폴더가 목록에 있는가 | 내용·유효성 |
| 5 | 백업 안 **SQLite `integrity_check`** | DB 구조가 정상인가 | DB 간 논리 일관성 |
| 6 | **SHA-256 대조**(원본 ↔ 복사본) | 복사하며 바이트가 깨지지 않았는가 | 백업 내용이 올바른가 |
| 7 | **별도 환경에 실제 복원 + 서비스 실행** | 정말 되돌릴 수 있는가 | — **이 기록에서 한 번도 안 함** |

### 5.1 명령 모음

```bash
# 서버 Ubuntu — 암호화 백업: 복호화 + 목록 검사
bash -o pipefail -c 'gpg --no-symkey-cache --decrypt "$HOME/<백업_폴더>/<백업이름>.tar.gz.gpg" | tar -tzf - > /dev/null; echo "검사 종료 코드: ${PIPESTATUS[*]}"'
```

```bash
# 서버 Ubuntu — 비암호화 백업: 압축·해시
gzip -t <서버_홈>/<백업_폴더>/<백업이름>.tar.gz
(cd <서버_홈>/<백업_폴더> && umask 077 && sha256sum <백업이름>.tar.gz > SHA256SUMS.txt)
(cd <서버_홈>/<백업_폴더> && sha256sum -c SHA256SUMS.txt)
```

```bash
# 서버 Ubuntu — 목록이 기대한 최상위 폴더로 시작하는지, 항목 수는 얼마인지
tar -tzf <서버_홈>/<백업_폴더>/<백업이름>.tar.gz | wc -l
tar -tzf <서버_홈>/<백업_폴더>/<백업이름>.tar.gz | awk -F/ '{c[$1]++} END{for(k in c) print k, c[k]}'
```

내용을 출력하지 않고 **목록에서 경로만** 검사합니다. 레거시 4차에서는 13개 항목(설정 파일, 인증 관련 파일, Gateway 서비스, `.claude`/`.codex` 폴더, 실행 파일, SSH 폴더, 예약 작업 정의, DB 복사본 3개 등)이 모두 포함된 것을 확인했습니다. **파일이 있다는 것만 확인한 것이며 로그인이 유효한지는 확인하지 않았습니다.**

### 5.3 "항목 수"의 의미

폰 백업은 항목 296,700개(`home` 134,090, `usr` 162,610, 기타 0)로 확인했습니다. 이는 **파일·폴더를 합친 목록 수**일 뿐, 필수 파일이 다 있다거나 복원된다는 증거가 아닙니다.

## 10. 보관과 정리 원칙

1. **기존 백업은 삭제하지 않는다.** 정리는 "삭제 후보 → 양쪽 경로 제시 → 사용자의 **명시적 최종 승인**" 순서입니다.
2. **이전 날짜의 백업 최소 한 세트를 남깁니다.** 새 백업이 잘못되었을 때를 대비합니다.
3. **복원 가능성이 검증되기 전에는** 오래된 백업을 정리하지 않습니다.
4. 정리 전에 **해시로 중복 여부를 확인**합니다. 해시가 같으면 내용 보존에 손실이 없지만, 지우기 전 **다시 대조**합니다.
5. 용량 때문에 정리할 때는 **복원 가능성이 확인된 최신 세트 + 직전 세트**를 우선 남깁니다.
6. **백업 이름 규칙**을 정합니다: `<대상>_<날짜>_<차수>_<상태>`(예: `…_1차_정상전송`).
7. 백업을 만들 때 **함께 만드는 문서**: 백업 범위, 제외 항목, 사용한 명령, 기준일, 경고, 해시, 검증 결과, **미검증 항목**.

## 11. 복원 — 계획만 있음, 실행하지 않았음

> **이 장의 명령은 검토용 예시입니다. 이 기록에서 실제 복원은 한 번도 하지 않았습니다. 복원 성공을 보증하지 않습니다.**

### 11.1 언제 복원하나

- 장애가 났거나 설정이 오염되어 **되돌릴 필요가 생긴 때**. 그렇지 않으면 운영 중인 정상 환경에 복원 시험을 하지 않습니다.
- 가장 안전한 방법은 **별도 환경(다른 폴더, 가상 머신, 다른 컴퓨터)에서 먼저 시험 복원**하는 것입니다.

### 11.2 복원 전 반드시 확인

1. 사용할 백업의 **해시를 다시 대조**(6장).
2. **현재 상태를 한 번 더 백업**(복원이 잘못되었을 때 되돌릴 길).
3. 원본 폴더를 **덮어쓰지 않는다.** 기존 것은 이름을 바꿔 **별도 보존**.
4. **기존 운영 환경의 폴더에 바로 풀지 않는다.** 다른 팀·다른 환경의 경로에는 절대 풀지 않는다.
5. 실행 중 프로세스, Gateway, 예약 작업, 열린 DB 확인. **중복 Gateway가 뜨지 않도록** 계획(같은 봇이 둘이 뜨면 충돌).
6. 여유 디스크와 권한 확인.
7. 목록(`tar -tzf`)의 **최상위 경로**가 기대한 폴더인지 확인.
8. **계정 정보(UID/GID·홈·셸)** 가 다르면 그대로 덮어쓰지 않고 소유권·권한 처리를 따로 계획.
9. 사용자 **승인**을 받는다.

### 11.3 안전한 복원 순서 (예시)

```bash
# 서버 Ubuntu — 1단계: 임시 폴더에 시험 압축 해제(운영 경로 아님)
mkdir -m 700 <서버_홈>/restore-test-<날짜>
tar -C <서버_홈>/restore-test-<날짜> -xzf <서버_홈>/<백업_폴더>/<백업이름>.tar.gz
```

암호화 백업이면:

```bash
# 서버 Ubuntu — 복호화와 해제를 파이프로 (임시 폴더로)
gpg --no-symkey-cache --decrypt <서버_홈>/<백업_폴더>/<백업이름>.tar.gz.gpg | tar -C <서버_홈>/restore-test-<날짜> -xzf -
```

2단계 이후는 **복원 대상 환경에서**:

1. 풀린 **파일 구조, 권한, 심볼릭 링크 대상**을 검토
2. **인증 파일·설정**이 있는지 확인(내용은 출력하지 않음)
3. **SQLite 복사본을 운영 경로로 명시적으로 배치**(4.3). 운영 DB 파일과 `-wal`/`-shm`이 섞이지 않게
4. 가상환경의 **절대 경로**, `HERMES_HOME`, 서비스 파일의 경로 **재확인**
5. 서비스 정의를 반영하고 필요한 설정(`systemctl --user` 서비스, linger 등)을 확인
6. 서비스 시작 → 상태·로그 확인
7. **인증이 살아 있는지** 확인. 만료되었으면 **재로그인**이 필요할 수 있음
8. 메모리에만 있던 자료는 **수동 재준비**
9. 아래 복원 후 점검표 수행

### 11.4 폰 복원 주의

- 정상 동작 중인 폰에 **시험 삼아 덮어쓰지 않습니다.**
- 대상 Android 버전, Termux 설치 방식, 앱 권한, PRoot 실행 조건, 저장 공간을 먼저 확인합니다.
- **Android 설정**(배터리 예외, USB 디버깅 승인, 앱 설치)은 백업에 없으므로 **다시 설정**해야 합니다.
- 복원 후 **같은 Gateway가 두 군데에서 뜨지 않게** 합니다.

### 11.5 복원 후 점검표 (복원 시험을 한다면)

```text
[ ] SSH 접속
[ ] Hermes 명령 시작, 버전 확인
[ ] 서비스(Gateway) active/running, 로그에 연결 성공
[ ] 메신저에서 실제 질문 → 응답, 완료 표시
[ ] 두 모델 호출(Claude·GPT) 정상, 지코 위임이 실제로 완료
[ ] 스킬 로딩, 승인형 보호 동작
[ ] 예약 작업이 의도대로(중복 발송 없음)
[ ] 인증 정상(만료 시 재로그인 경로 확인)
[ ] SQLite 무결성(integrity_check)
```

### 11.6 오류 대응

| 증상 | 하지 말 것 | 할 것 |
| --- | --- | --- |
| `sha256sum -c` / 해시 불일치 | 해시 파일을 고쳐서 맞추기 | 파일 사용 중단, 원본과 비교, 정상 백업에서 다시 복사 |
| `tar -tzf` 오류 | 그대로 풀어 운영에 투입 | 압축 손상 가능성, 중단 |
| GPG 복호화 실패 | 암호를 채팅에 쓰기 | 암호 확인, 다른 차수 백업 시도 |
| `Permission denied` | `chmod 777` | 소유권·권한 확인 |
| `No space left on device` | 원본·기존 백업 삭제 | 저장 공간 확인 |
| 복원 후 인증 실패 | 인증 파일 덮어쓰기, 키 무단 갱신 | 인증 경로를 읽기 전용으로 점검, 필요하면 재로그인 |

### 12.3 작성자 권장 (기록이 아니라 일반 권고)

- **가장 먼저 해 볼 일은 복원 시험입니다.** 가장 작은 백업(예: 일반협업팀 백업)으로 **별도 폴더에 풀어 서비스 없이 구조만** 확인하는 것부터 시작하세요. 복원해 본 적 없는 백업은 믿기 어렵습니다.
- 비암호화 백업을 PC나 외부 저장소에 둘 때는 **암호화(예: GPG)** 를 권장합니다.
- 백업 도중 변경 경고를 줄이려면 **서비스 정지 후 백업**을 기본으로 하는 것을 고려하세요(정지 시간 안내 포함).
- 백업마다 **"복원 시험 결과"** 칸이 있는 기록표를 두세요.

## 부록 A. 빠른 점검표 (백업을 만들 때)

```text
[ ] 장비 확인(PC / 서버 / 폰)
[ ] 읽기 전용 조사: 용량·권한·여유 공간
[ ] 같은 이름 백업이 없는가 (있으면 중단)
[ ] 비밀값은 내용을 출력하지 않았는가
[ ] DB는 온라인 백업 복사본으로 넣었는가
[ ] 종료 코드가 모두 0인가 (아니면 경고 원인 기록)
[ ] gzip -t, tar -tzf, 핵심 경로 확인
[ ] SHA-256 생성, PC에서 다시 대조
[ ] 암호/권한/PC 폴더 권한 확인
[ ] 복원 시험 여부를 정직하게 기록 ("미실시"도 기록)
[ ] 기존 백업은 건드리지 않았는가
```

## 부록 B. 하지 말아야 할 것

- 기존 백업을 **덮어쓰기·삭제·이동**
- 운영 중인 환경에 **시험 삼아 복원**
- 해시 파일을 **수정**해서 일치시키기
- 백업 비밀번호·토큰을 채팅·문서에 쓰기
- 백업 파일을 채팅·공유 드라이브에 올리기
- 해시·압축 검사 통과만으로 **"복원 가능"이라고 말하기**
- 백업을 위해 **유료 API**를 켜기
- 검사 명령이 실패했는데 삭제를 계속하기
