# 서버에 AI 연구 협업 방을 Discord로 만들고 운영한 방법 (비전문가용)

> 이 글은 개인 서버에 'AI 여러 개가 함께 일하는 연구 방'을 Discord로 구축하고 운영한 **시스템·운영 방법만** 정리한 기록입니다. 투자 조언이 아니며, 종목 추천·매매 의견·특정 종목 분석 결과는 하나도 담지 않았습니다.
> 실제로 해 본 것(봇 5개 생성, 비공개 방 5개, 연결, 서비스 등록, 백업)과 계획만 세운 것(자동 복구, 재부팅 후 복원, 백업 복원 시험 등)을 구분해 적었고, 자료로 확인되지 않은 것은 '미확인', 짐작은 '추정'이라고 표시했습니다.
> 개인정보 보호를 위해 이름·주소·번호·키는 모두 `<자리표시자>`로 바꿨습니다. 그대로 따라 하려면 본인 값으로 바꿔 넣으세요.

---

## 0. 먼저 읽기

### 0-1. 이 글의 결론

- 서버 한 대 안에 **주식 연구 전용 AI 팀**을 따로 만들고 Discord에서 대화하도록 연결했습니다. AI는 기본 3개(서로 다른 회사 모델 3종)와 필요할 때만 쓰는 예비 2개입니다.
- Discord에 **봇 5개 + 비공개 방 5개**를 만들었고 5개 모두 답장을 받았습니다.
- 서버가 계속 일하도록 **서비스로 등록**했고, 접속 창(SSH)을 닫아도 답장이 오는 것까지 확인했습니다.
- 안 해 본 것: 서버 실제 재부팅 시험, 장애를 일부러 일으키는 시험, 백업 실제 복원 시험은 **미실시**입니다.

### 0-2. 자리표시자 설명

`<서버_주소>`(서버 접속 주소), `<관리_계정>`(SSH 접속용 일반 계정), `<실행_계정>`(AI 팀 전용 새 리눅스 계정), `<주식팀_폴더>`(프로그램 설치 폴더), `<데이터_폴더>`(설정·기록·비밀 파일 폴더), `<게이트웨이_서비스>`(Discord와 AI를 잇는 서비스 이름), `<서버_이름>`(만든 Discord 대화 공간 이름), `<봇_이름1>`~`<봇_이름5>`(봇 5개), `<내_번호>`(내 Discord 사용자 번호), `<채널_번호>`(방 번호), `<토큰>`(봇 비밀번호 격인 긴 글자, **절대 어디에도 적지 않습니다**). 모두 본인 값으로 바꿔 쓰세요.

### 0-3. 처음 보는 말 풀이

- **서버(컴퓨터)**: 항상 켜 두는 컴퓨터(여기서는 Ubuntu 리눅스 작은 PC). **Discord 서버**는 다른 것으로, 방들이 모인 '건물'입니다. 이 글에서는 Discord 서버를 **대화 공간**이라 부릅니다.
- **채널**: 대화 공간 안의 방. **비공개 채널**은 허락된 사람·봇만 보입니다.
- **봇**: Discord 안에서 말하는 로봇 계정. AI가 이 계정으로 말합니다. **토큰**은 봇의 비밀번호 겸 출입증이라 가진 사람은 봇을 마음대로 조종합니다.
- **Gateway(게이트웨이)**: AI 프로그램(Hermes)과 Discord를 이어 주는 출입문 프로그램. 켜져 있어야 봇이 온라인입니다. Hermes는 이 구축에 쓴 AI 에이전트 프로그램 이름입니다.
- **프로필**: AI 한 명분의 설정 묶음(모델, 지침, 비밀 등). **SSH**: 내 PC에서 서버를 원격 조종하는 접속 방법. **systemd 서비스**: 서버가 켜질 때 프로그램을 자동 시작하고 꺼지면 다시 켜 주는 리눅스 기능.

### 0-4. 이 글의 근거

사용자가 직접 실행한 터미널 출력과 Discord 화면을 기록한 인수인계 문서들(2026-11-12~16 작성)입니다. 이 글을 쓰며 서버에 새로 접속해 확인한 것은 없고, 상태는 기록 시점 기준입니다.

## 1. 준비

### 1-1. 필요한 것

항상 켜 둘 서버 한 대(이 구축은 메모리 약 8GB의 작은 PC, Ubuntu), 서버에 SSH로 접속할 내 PC(Windows), 서버 계정 2개(접속용 `<관리_계정>`, AI 팀 전용 `<실행_계정>`), Discord 계정(이메일·전화번호 인증이 요구될 수 있음), AI 이용권(회사별로 구독 로그인 또는 API 키)이 필요합니다.

### 1-2. 지켜야 할 약속

1. **조회와 변경을 구분**합니다. 먼저 읽기만 하는 점검, 변경은 승인 후.
2. 명령은 **한 번에 하나씩**, 내 PC에서 칠지 서버에서 칠지 먼저 밝힙니다. 출력 결과나 프롬프트를 명령으로 다시 붙여 넣는 실수가 실제로 있었습니다(11장).
3. **기존 환경은 건드리지 않습니다.** 새 팀은 새 계정에 따로 만듭니다.
4. **토큰·키·비밀번호는 대화창, 스크린샷, 문서에 올리지 않습니다.** 숨김 입력 칸에만 넣습니다.
5. **백업과 삭제는 내가 요청할 때만** 합니다.
6. 실제 매매·주문은 하지 않습니다. 이 방은 자료 정리와 반대 의견 점검용입니다.

## 2. 설계: 왜 이렇게 만들었나

### 2-1. 별도 리눅스 계정으로 분리 (B안)

- **왜**: 서버에 이미 일반 협업용 AI 팀이 돌고 있었습니다. 같은 계정에 얹으면 설정·인증이 섞여 서로를 망가뜨릴 수 있습니다.
- **무엇을**: AI 연구 팀 전용 계정 `<실행_계정>`(관리자 권한 없는 일반 계정)을 새로 만들고 프로그램·가상환경·데이터·서비스·백업을 모두 그 아래에 두었습니다.
- **한계**: 파일·프로세스 권한은 분리되지만 같은 서버의 CPU·메모리·디스크는 함께 씁니다. 별도 서버 수준의 완전한 격리는 아닙니다.
- **확인된 결과**: 설치 전 읽기 전용 점검 계획(계정 충돌, 서비스·포트, 디스크, 메모리, 인증 호환성 등 11항목)을 세우고 설계 승인 후 단계별로 설치했습니다.

### 2-2. 프로그램·프로필·봇의 구성 유형

- A(프로그램 1·프로필 1·봇 1): 가능(문서 확인). B(프로그램 1·프로필 1·봇 5): 방법을 못 찾아 보류. **C(프로그램 1·프로필 5·봇 5): 가능(문서 확인), 실제 채택.** D(프로그램 5·프로필 5·봇 5): 가능하나 문서가 새로 만들기를 지양하라고 안내.
- C에서는 서비스(게이트웨이) **한 개**가 AI 5개의 봇을 모두 처리합니다. 독립된 서버 5개가 아닙니다. 게이트웨이가 반복해서 멈출 때만 D를 검토하기로 했습니다(실제 검토는 안 함).
- 처음엔 봇 1개 안이었으나 독립성 검토 요청으로 **봇 5개 + 비공개 방 5개**로 정했습니다. 봇이 많다고 분석이 저절로 독립되지는 않으며, 최초 분석 전에 다른 AI의 결론을 주지 않는 운영이 더 중요합니다.

### 2-3. AI 5개의 역할

- 기본 3개: 팀장(Claude 계열, 구독 로그인 방식, 질문 정리·종합), 독립 분석 A(GPT 계열, 구독 로그인), 독립 분석 B(Gemini 계열, API 키라 사용량만큼 과금).
- 예비 2개: 예비 1(Claude 상위 모델, API 크레딧이라 과금), 예비 2(GPT 계열 추가, 구독 로그인). 의견이 갈리거나 중요할 때 씁니다.
- 5개는 '5표'가 아니라 **3계통**(같은 회사 모델 둘은 같은 방향으로 틀릴 수 있음)입니다. 팀장의 구독 방식과 예비 1의 API 방식은 **서로 다른 인증**이라 혼동하지 않는 것이 규칙이었습니다.
- 예비 호출은 처음 '사용자 승인 후'였다가 이후 '중요 판단·의견 충돌·기본 AI 장애 때 팀장 판단으로 자동 추가'로 바뀌었습니다(두 시점 기록이 모두 있으니 최신 정책은 운영 문서로 확인).
- 업무 분담은 **임시안**입니다. 모델별 강점 근거는 찾지 못했고 오류 기록을 보며 조정하기로 했습니다.

## 3. 서버에 AI 팀 설치 (요약)

Discord 이전 단계라 요약만 합니다. 목적은 '붙이기 전에 AI가 각자 단독으로 응답하는지' 확인입니다.

1. 새 계정 `<실행_계정>` 아래에 `<주식팀_폴더>`를 만들고 프로그램을 설치했습니다.
2. AI별 인증을 따로 등록했습니다. 기존 팀의 키·토큰은 **복사하지 않고** 새로 로그인하거나 숨김 입력으로 붙여 넣었습니다. (기존 환경의 키를 프로그램으로 읽어 새 계정에 자동 전달하려던 시도는 멈춰서 폐기했습니다.)
3. 각 AI에 짧은 연결 시험 문장을 보냈습니다.
4. 서버 안에서 `sudo -u <실행_계정> -H ...` 형태로 AI 팀 명령을 실행했습니다. `sudo`는 서버 안에서만 있는 명령이라 내 Windows에서 바로 치면 '명령 없음'이 나옵니다.

**확인된 결과**: AI 3종(Claude, GPT, Gemini) 각각의 단독 응답 성공을 실제 출력으로 확인했습니다. 이 시점엔 AI끼리의 위임·교차검증과 Discord가 아직 없었습니다.

## 4. Discord 계정과 대화 공간 만들기

### 4-1. 계정과 개발자 모드

1. 내 PC 브라우저에서 Discord 계정을 만들고 로그인했습니다(이메일·전화번호 인증을 거침). 이메일 비밀번호, Discord 비밀번호, 봇 토큰은 모두 별개입니다.
2. 설정에서 **개발자 모드**를 켰습니다. 번호(ID) 복사 기능이 여기에 있습니다.
3. 내 사용자 ID를 복사해 두었습니다(`<내_번호>`).

**막혔던 일**: 이름을 우클릭해도 메뉴가 안 떴습니다. **내 프로필을 왼쪽 클릭 → 맨 아래 '사용자 ID 복사'**로 해결했습니다.

### 4-2. 대화 공간 만들기

새로 `<서버_이름>`이라는 **나 혼자(믿는 사람만) 쓰는 개인 대화 공간**을 만들었습니다. 남이 들어올 수 있는 공간에 봇을 넣으면 허용 범위를 잘못 잡았을 때 위험하기 때문입니다.

## 5. 봇 5개 만들기와 초대

AI 1개당 봇 1개, 총 5개를 같은 절차로 만들었습니다.

### 5-1. 순서

1. Discord 개발자 포털(discord.com/developers)에서 **New Application**(신청서)을 만듭니다. 이름은 `<봇_이름1>`처럼 구분되게 짓습니다.
2. **Bot 메뉴**에서 **Message Content Intent**를 켜고 **Save Changes(저장)**를 누릅니다. Intent는 '봇이 이 정보를 봐도 되나요?'라는 허락 항목으로, 꺼져 있으면 봇이 글을 못 읽거나 접속이 거절되어 기록상 '봇이 안 되는 1순위 원인'입니다. 저장을 안 누르면 도로 꺼집니다. 이번에는 Presence Intent, Server Members Intent를 **꺼 둔 채** 허용 사용자를 번호로 지정해 문제가 없었습니다(사전 학습 문서는 후자를 '필수'로 적었으나 실제로는 필수가 아니었으니 화면 안내를 우선하세요).
3. 설치는 **서버(길드) 설치만** 켜고 사용자 설치는 끕니다. 범위(Scope)는 `bot`과 `applications.commands`입니다.
4. 권한은 **최소한**만: 채널 보기, 메시지 보내기, 메시지 기록 보기, 공개 스레드 만들기, 스레드에서 메시지 보내기. **관리자 권한은 주지 않았고** 음성·파일·이모지는 필요해질 때 따로 판단하기로 했습니다.
5. 초대 링크를 열어 `<서버_이름>`에 봇을 넣습니다. 5개 모두 초대 성공 화면과 '일반' 채널의 앱 추가 기록을 확인했습니다.
6. **봇 토큰**은 Bot 메뉴의 **Reset Token**으로 받습니다. 한 번만 보이므로 바로 7장처럼 숨김 입력으로 처리하고, 노출됐다면 즉시 다시 발급합니다.

### 5-2. 막혔던 일과 결과

- 초대 링크 복사 버튼을 브라우저 확장 프로그램 아이콘과 혼동했습니다. **신청서의 Application ID로 설치 링크를 직접 만들어** 해결했고 봇을 다시 만들 필요는 없었습니다.
- 결과: 봇 5개 생성·초대 성공(화면 확인), 토큰 5개는 서로 다름(파일 점검 확인).

## 6. 비공개 방 5개와 내 번호 연결

### 6-1. 방 만들기

- AI 1개당 비공개 텍스트 방 1개, 이름은 역할이 드러나게 지었습니다. 만들 때 **'비공개 채널' 스위치**를 켜고 멤버 선택에서 **역할이 아닌 해당 봇 하나**를 골랐습니다.
- 결과: 5개 방 모두 접근 목록이 '나 + 해당 봇'뿐인 것을 화면으로 확인했습니다.
- 처음 만든 방이 '음성 채널' 구역 아래라 '채팅 채널' 구역으로 옮겼습니다. '카테고리와 권한이 동기화되지 않았다'는 안내가 뜨는데 방별 비공개 설정 때문이므로 **'지금 동기화하기'는 누르지 않았습니다.**

### 6-2. 방과 AI의 관계

팀장 방은 내부 협업 결과를 모으는 창구, 나머지 방은 해당 AI와 직접 대화하는 창구입니다. 설계 문서에 9개 채널 구성안이 있었으나 그것은 **제안이었고 구축한 것은 위의 5개 비공개 방**입니다. **미확인**: 봇이 다른 봇의 방을 못 읽는지(다른 봇의 글을 무시하는 기본값만 확인, 전 경로 미시험). 방 분리는 같은 서버 계정 안의 파일 접근을 막는 강한 보안이 아닙니다.

## 7. Hermes에 연결하기 (토큰·허용 명단·홈 채널)

### 7-1. 설정 마법사

각 AI(프로필)마다 설정 마법사를 한 번씩 실행했습니다. 기본 프로필:

```bash
sudo -u <실행_계정> -H env HERMES_HOME=<데이터_폴더> <주식팀_폴더>/.venv/bin/hermes gateway setup
```

나머지 4개는 `--profile <프로필_이름>`을 `gateway` 앞에 붙여 같은 방식으로 반복했습니다.

마법사에서 한 일:
1. 메뉴에서 Discord 선택.
2. 해당 봇의 **토큰을 숨김 입력**으로 붙여 넣기. 마법사가 토큰이 맞는지, Message Content Intent가 켜졌는지 검사해 줍니다(실제 화면에서 '토큰 정상, 저장됨, Intent 켜짐' 확인).
3. **'나 자신 허용'에 y**, '다른 허용 사용자'는 비워 둠 → **허용 명단에 `<내_번호>`만** 들어갑니다.
4. **홈 채널**(알림이 기본 도착하는 방)에 그 AI의 방 번호 `<채널_번호>` 입력.
5. 마지막에 '지금 시작?'과 '자동 시작?'에는 **둘 다 n**. 아직 연결을 켜지 않고 설정만 저장했습니다.

> 허용 명단이 비어 있으면 기본으로 아무도 못 씁니다. 허용된 사람은 AI의 모든 기능(도구 사용 포함)을 쓸 수 있으므로 **믿는 사람만, 개인용이면 내 번호만** 넣습니다.

### 7-2. 저장 결과 점검 (파일 수준)

5개 프로필의 비밀 파일(`.env`)을 읽어 **값은 출력하지 않고** 점검했습니다. 파일 소유자가 `<실행_계정>`, 권한 600(소유자만 읽기·쓰기), 토큰 항목 정확히 1개, 허용 사용자가 나 하나뿐, 홈 채널 번호 일치가 **5개 모두 True**였고, 토큰 5개가 서로 다른 것도 확인했습니다. 

### 7-3. 막혔던 일

- 하위 프로필 설정 종료 때 '이 프로필은 자기 게이트웨이를 갖지 않는다'는 안내가 나왔습니다. 게이트웨이를 하나만 쓰는 구성이라 나오는 안내였고, 위 파일 점검으로 저장을 확인했습니다. `--force` 같은 옵션은 쓰지 않았습니다.
- 첫 봇 설정 화면에 '봇이 아직 서버에 없다'는 안내가 떴지만 이미 초대에 성공한 상태와 달랐습니다. 원인은 미확정(추정: 접속 전 대략값 기반)이며 재초대 없이 실제 연결에서 정상 응답했습니다.

## 8. 게이트웨이 켜기 → 서비스로 등록

### 8-1. 처음 상태

- 처음 `gateway status`는 '실행 안 함'이었고 마지막 종료 사유는 **'자동 시작된 게이트웨이가 600초 동안 유휴 상태라 종료'**였습니다. 장애가 아니라 정해진 동작입니다.

### 8-2. 수동으로 켜서 시험

```bash
sudo -u <실행_계정> -H env HERMES_HOME=<데이터_폴더> <주식팀_폴더>/.venv/bin/hermes gateway run
```

이 창을 열어 둔 채 다른 SSH 창에서 실행 상태를 조회했고, Discord에서 **봇 5개를 각각 `@`로 불러**(서버 방에서는 `@`로 지목해야 답합니다) 짧은 답변을 받았습니다. **5개 모두 실제 답변 확인.**

### 8-3. 서비스로 등록 (부팅 시 자동 시작)

수동 실행은 창을 닫으면 끝나므로, 실행 계정을 `<실행_계정>`으로 지정한 시스템 서비스로 설치했습니다(지금 바로 시작은 하지 않음).

```bash
sudo env HERMES_HOME=<데이터_폴더> <주식팀_폴더>/.venv/bin/hermes gateway install --system --run-as-user <실행_계정> --no-start-now --start-on-login
```

서비스 이름이 `<게이트웨이_서비스>`입니다. 설정 핵심: 실행 계정은 `<실행_계정>`, 비정상 종료 시 5초 후 재시작(`Restart=always`), 단 '설정 오류'를 뜻하는 종료 코드 78은 재시작하지 않음. 수동 창은 Ctrl+C 한 번으로 정상 종료한 뒤 서비스를 시작하고 상태를 조회했습니다.

```bash
sudo systemctl start <게이트웨이_서비스>
systemctl show <게이트웨이_서비스> -p ActiveState -p SubState -p NRestarts -p UnitFileState
```

### 8-4. 확인된 결과

서비스 상태 active/running/enabled(재시작 횟수 0). SSH 접속을 끊은 뒤에도, 서비스 정상 재시작 뒤 기존 스레드에서도, 휴대폰 Discord 앱에서도 질문에 **답변 성공**.

### 8-5. 경고와 한계

- 서비스 시작 때 데이터베이스 모드 전환 경고가 나왔으나 재설치나 임의 변경은 하지 않았습니다.
- **정상 재시작 성공은 장애 자동 복구나 실제 재부팅 성공의 증거가 아닙니다.** (미검증)

## 9. AI끼리 일하는 규칙과 지침 파일 구조

> 이 장은 **'어떤 종류의 지침이 있고 AI의 행동을 어떻게 나누는가'**만 설명합니다. 지침 속 분석 내용은 적지 않습니다.

### 9-1. 협업 방식

- 팀장 AI가 질문을 정리해 다른 AI에게 **위임**합니다. 순서: 질문 정리 → 각 AI **서로 못 보고 독립 분석** → 핵심 수치를 '분석하지 않은 쪽'이 원문과 대조 → 의견 일치 정도를 표로 정리 → 팀장 종합 → 사람이 확인·결정·기록. 토론은 최대 1~2라운드로 제한하는 안입니다.
- 위임 기록은 서버에 위임 번호별 폴더(요약 파일과 작업 로그)로 남아, 실제로 어떤 모델이 일했는지 나중에 확인할 수 있습니다.

### 9-2. 실제로 해 본 것

간단한 비금융 질문을 5개 AI에 위임해 모두 완료 기록을 확인했고, 가상 기업으로 기본 AI 위임과 중요 판단 상황의 4개 위임 완료도 확인했습니다. 위임 로그 일부가 `…(+N chars)`로 잘려 **전체 입력과 지시 준수까지 감사한 것은 아닙니다.**

### 9-3. 장애 대응 정책 (A안: 조건부 분석 지속)

- 성공한 분석은 보존하고, 실패·중단·시간 초과·잘림은 **숨기지 않고 표시**합니다.
- 기본 AI가 실패하면 예비 AI로 검증을 시도하되 **원래 AI로 사칭하지 않고** 실제 호출을 보고합니다.
- 독립 검증 부족, 핵심 자료 불신, 중대한 의견 충돌 미해결, 팀장 자체 실패 때는 **최종 판단을 보류**하고, 일부만 성공했으면 '제한적·참고용'으로 표시합니다.
- 구현: 위임 결과에 상태 표시(정상/제한/중단 3종)를 덧붙이는 작은 플러그인. 모의 시험 3종(전부 성공/일부 실패/전부 실패)과 공식 진단은 통과했습니다.
- **미검증**: 실제 외부 장애의 자동 복구. 외부 서비스 일시 오류(503)와 요청 제한(429)이 실제로 있었으나 재시도 후 작업은 완료되었고, 복구 경로는 소스 코드상 '추정'일 뿐 성공 로그는 없습니다.

### 9-4. 지침 파일의 종류 (구조만)

| 종류 | 역할 |
|---|---|
| 팀장 지침(`SOUL.md`) | 팀장 AI의 정체성·원칙, 장애 대응 정책 |
| 하위 AI 지침(`SOUL.md`, 프로필별 4곳) | 각 AI의 정체성·원칙 |
| 운영 규칙 문서(스킬) | 도구 사용법, 자료 한계 표시, 오류 보고, 판단 보류 조건 |
| 공통 규칙(설계 문서) | 모든 AI에 붙이는 공통 지침. 출처·기준일 표기, 독립 분석 우선, 계산은 프로그램·AI는 해석만, 모르면 '미확인', 주문·키 금지, 호출 기록, 모든 답 끝에 '투자 조언 아님' |
| 방식별 스타일 지침 5종(설계 문서) | 투자 방식별로 나뉘며 모두 같은 틀: 대상 기간 → 우선 볼 영역 → 필요한 데이터 → AI 임시 분담 → 진행 순서 → 특별한 위험 → 사용자 요청 틀 → 보고서 양식 → 주의 |
| 사용자 규칙 칸(공통 규칙 문서) | 사람만 정할 값. 비어 있으면 '미정'으로 두고 가정을 보고서에 적음 |

- 원리: **공통 규칙이 모든 스타일 지침보다 앞서고**, 스타일 지침은 '무엇을 먼저 볼지'만 정합니다.
- 역할 지침(특정 인격 부여)은 최소화했습니다(작은 모델에서 정확도를 낮췄다는 보고가 있으나 큰 모델은 미검증이라 임시 결정).
- 스타일 지침 5종을 서버에 실제 반영해 시험한 기록은 이 자료에서 확인되지 않았습니다(미확인).

## 10. 자료 연결과 백업

### 10-1. 공시·가격 자료를 AI에게 먹이는 구조 (시스템 구조만)

- **원칙**: 숫자는 **프로그램이 공식 출처에서 받아 표로 만들고**, AI는 표를 해석만 합니다. 출처 없는 숫자는 '미확인'.
- 수집기는 자료 종류별로 두었고, 조회 → 검증 → 메모리에 올림 순서로 동작합니다. 인증키는 처음엔 숨김 입력, 이후 보호 파일(폴더 700·파일 600)에 등록해 수집기만 내부에서 씁니다.
- AI 도구는 **메모리 자료만 읽고 외부 API나 키에 접근하지 않으며**, 조건이 안 맞으면 다른 기간·기업 값으로 대신하지 않고 '보류'를 돌려줍니다.
- 자료는 메모리에만 있어 **서버가 꺼지면 사라지고 자동 갱신·재부팅 후 자동 복원은 없습니다.** 최신성·정정 여부·원문 일치는 확인 범위가 한정되어 일부 미완료입니다.

### 10-2. 백업

- 서버의 AI 팀 폴더 전체(약 5GB)를 압축해 약 4GB 파일 1개로 만들었습니다(항목 약 9만 7천 개). 백업 중에는 게이트웨이만 정상 중지했다가 다시 켰고 active/running/enabled를 확인했습니다.
- 검증: 압축·목록 읽기, 필수 코드·5개 프로필 존재 확인, 내 PC로 복사한 뒤 크기·해시 일치 확인(통신용 임시 파일 7개는 제외됨).
- **주의**: 백업 파일은 **암호화되어 있지 않고 인증 관련 파일을 포함할 수 있습니다.** 서버에서는 폴더 700·파일 600으로 제한했고 채팅·Discord·공유 드라이브에는 올리지 않습니다. 내 PC에서의 접근 권한은 따로 확인해야 합니다.
- **범위 밖**: 운영체제 전체, 다른 팀, 실행 중 메모리 자료. **복원 시험은 미실시**입니다. 계획은 별도 폴더에서 목록 확인 → 계정 번호(UID/GID) 대조 → 게이트웨이 정지 → 검토한 범위만 복원 → 서비스·로그 확인 → 자료 수동 재준비입니다(운영 폴더에 바로 풀지 않음).

## 12. 확인하지 못한 것

- 서버를 실제로 재부팅한 뒤 서비스 자동 시작: **미확인**(enabled 등록만 확인)
- 비정상 종료 때의 자동 복구: **미확인**(정상 재시작만 확인)
- 백업으로 실제 복원: **미실시**
- 봇의 다른 방 접근 거부 전 경로 시험, 실제 유효 권한 전체 감사: **미확인**
- 5개 프로필 모두 개별 Discord 세션에서 모든 도구 확인: 일부만 확인(나머지는 코드 연결·문법 확인)
- 자료 자동 갱신, 재부팅 후 자료 자동 복원: 구현 안 됨. 모든 종목·시장으로의 확장: 미완료
- 스타일 지침 5종의 실제 적용·성능, 스킬 자동 개선의 승인 이력 감사: **미확인**
- 시스템 결과의 정확도·수익성: **검증 안 됨.** 자료 정리와 반대 의견 점검 보조일 뿐입니다

## 13. 한 줄 정리

**'새 리눅스 계정에 AI 팀을 따로 설치하고, Discord에서 봇 5개와 비공개 방 5개를 만들어 토큰은 숨김 입력으로 저장하고 허용 명단은 내 번호만 넣은 뒤, 하나의 게이트웨이를 서비스로 등록했으며, 재부팅·장애 복구·복원은 아직 시험하지 않았다.'**
