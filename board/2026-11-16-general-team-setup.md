 일반협업팀 구축·운영·백업 매뉴얼 — 기존 Hermes를 건드리지 않고 새 협업 환경 만들기

* 목차
{:toc}


> 이 문서는 한 대의 Ubuntu 서버에서 **기존 Hermes Agent 운영 환경을 보존한 채**, 별도의 **신규 일반협업팀**(바코1=Claude 팀장, 지코1=GPT 독립 검증)을 구축·운영·백업한 2026년 11월 11~12일 기록을 초보자용으로 정리한 것입니다. **실제로 확인된 것과 확인하지 못한 것을 구분**했고, 서버 주소·계정·키·봇 이름·위임 ID·해시 값 같은 개인 정보는 `<…>` 자리표시자로 바꾸거나 싣지 않았습니다.

## 0. 먼저 읽기

### 0.1 이 매뉴얼의 성격

- 실제 작업 기록을 바탕으로 한 **구축·운영·백업 안내서**입니다.
- **처음부터 끝까지 그대로 따라 하면 재현된다는 보증서가 아닙니다.** 기록에 없는 단계(예: 모델·로그인 선택 화면의 구체 조작, 메신저 봇 생성 절차)는 만들어 쓰지 않았습니다. 해당 부분은 3장 끝과 12장에 따로 표시했습니다.
- AI 두 개가 어떻게 협업하는지(호출 규칙, 토론, 칸반 B1~B7)는 별도 **「AI 협업 운영 매뉴얼」**에서 자세히 다룹니다. 이 문서는 **환경을 만들고 지키는 방법**에 집중합니다.

### 0.2 자리표시자

| 자리표시자 | 의미 |
| --- | --- |
| `<서버_주소>` | 서버 접속 주소 |
| `<서버_계정>` | 서버 로그인 계정 |
| `<서버접속_키>` | PC에서 서버로 들어갈 때 쓰는 SSH 개인키 파일(이름·내용 모두 비공개) |
| `<서버_홈>` | 서버 계정의 홈 폴더 |
| `<백업_폴더>` | 백업을 모아 두는 폴더 |
| `<64자리_해시값>` | 백업 파일의 SHA-256 값 |
| `<날짜>` | 작업 날짜(예: 20261112 형식) |

### 0.3 명령을 어디서 치는가 — 가장 흔한 실수

| 표시 | 뜻 |
| --- | --- |
| **메인 PC PowerShell** | 내 Windows PC의 PowerShell. 서버에 `ssh`로 명령을 보낼 때 씀 |
| **서버 Ubuntu 터미널** | 서버에 로그인한 뒤의 셸 |

> 규칙: **명령은 한 번에 하나씩** 실행하고, 출력 결과를 확인한 뒤 다음으로 갑니다. 장비를 헷갈리면 명령이 엉뚱한 곳에서 실행됩니다.

### 0.4 지켜야 할 큰 원칙

1. **기존 환경은 보존한다.** 신규 환경이 충분히 검증되고 사용자가 따로 승인하기 전에는 기존 Hermes를 삭제·덮어쓰지 않습니다.
2. **인증 파일과 토큰은 읽지도 출력하지도 않는다.** 문서·채팅·로그에도 싣지 않습니다.
3. **추가 유료 API 과금 금지.** 구독 로그인을 유지하고, 별도 API 키 과금은 사용자의 명시적 승인이 있을 때만 씁니다.
4. **변경 전에 조회, 조회 후에 승인, 승인 후에 변경.**
5. **"설정에 이름이 있다" ≠ "실제로 동작한다".** 모델 이름이 목록에 있다고 독립 에이전트가 만들어진 것이 아닙니다.

## 1. 한눈에 보기

### 1.1 구성도

```text
서버 (Ubuntu, 물리 1대)
├─ 기존 Hermes 환경 ........ 그대로 보존 (삭제·덮어쓰기 금지)
├─ 신규 일반협업팀 ......... 독립 프로그램 + 독립 가상환경 + 독립 데이터
│    ├─ 바코1 (Claude, 팀장)
│    └─ 지코1 (GPT, 독립 검증 · 별도 프로필)
└─ 백업 폴더 ............... 1차 기준백업, 2차 정상상태백업
```

### 1.2 폴더 배치

| 구분 | 경로 |
| --- | --- |
| 기존 Hermes | `<서버_홈>/.hermes` (보존) |
| 신규 프로그램 | `<서버_홈>/hermes-new/hermes-agent` |
| 신규 가상환경 | `<서버_홈>/hermes-new/.venv` |
| 신규 데이터(`HERMES_HOME`) | `<서버_홈>/hermes-new/data` (권한 700) |
| 신규 Gateway 서비스 | 사용자 서비스 `hermes-general-gateway.service` |
| 백업 | `<서버_홈>/<백업_폴더>` |

핵심은 **신규 환경 전용 `HERMES_HOME`을 따로 두어** 기존 설정·인증·세션과 섞이지 않게 하는 것입니다.

### 1.3 역할

| 이름 | 모델 | 역할 |
| --- | --- | --- |
| 바코1 | Claude (구독 DirectSDK) | 팀장, 최종 통합 |
| 지코1 | GPT (Codex OAuth, 별도 프로필) | 독립 분석·검증 |
| 재코·바코2·지코2 | Gemini / Claude Opus / GPT 추가 | **사용자 지시 또는 승인 시에만** 호출. 삭제하지는 않음 |

### 1.4 2026-11-12 기준 상태 (검증 수준 구분)

| 항목 | 상태 |
| --- | --- |
| 신규 환경 설치 | 확인됨 |
| 바코1 한국어 응답 | 확인됨 |
| 지코1 위임이 **실제로 완료**됨(기록 3건) | 확인됨 |
| 메신저(Telegram) 신규 봇 연결, 실제 송수신 | 확인됨 (PC 웹 클라이언트 기준) |
| 1차·2차 백업 생성, 압축 검사, SHA-256 일치 | 확인됨 |
| **서버 재부팅 후 자동 시작** | 미검증 |
| **장애 자동 복구** | 미검증 |
| **백업 파일로 실제 복원** | 미검증 |
| 스마트폰 앱에서의 별도 시험 | 하지 않음 |

## 2. 준비물과 사전 점검

- Ubuntu 서버(계정 하나, SSH 접속 가능), Windows PC(PowerShell)
- 구독 로그인: Claude(Claude Code 로그인 상태), GPT(Codex OAuth)
- 여유 디스크: 신규 환경 약 2.7GB + 백업 2회분(각 약 1.8GB) → **여유 10GB 이상** 권장 (기록 당시 서버는 수백 GB 여유)
- 읽기 전용 점검을 먼저 합니다.

**메인 PC PowerShell — 서버에 접속해 한 줄 실행하는 형식**

```powershell
ssh -i "<서버접속_키>" <서버_계정>@<서버_주소> "<실행할 명령>"
```

**서버 Ubuntu 터미널 — 기존 Gateway 상태 확인(조회 전용)**

```bash
systemctl --user is-active hermes-gateway.service
```

> `active`는 "프로세스가 떠 있음"일 뿐 모델·메신저가 실제로 잘 된다는 증거가 아닙니다.

## 3. 신규 환경 설치

### 3.1 설치 전에 결정한 것

- 기존 환경의 `config.yaml`, `.env`, `auth.json`을 **복사하지 않는다.** 인증은 신규 환경에서 따로 연결합니다.
- 기존 Hermes의 소스·실행기·서비스는 지우지 않고 **이름만 바꿔 격리**(예: `…_삭제대기_<날짜>`)하는 방식을 썼습니다. 신규 서비스와 충돌하지 않게 하기 위함이며, **영구 삭제는 별도 승인 후**입니다.

### 3.2 설치 결과 (기록)

- 신규 Hermes 버전 `v0.23.x`, Python 3.14 계열
- 일반 `pip` 설치는 **의존성 충돌**(이미지 라이브러리 버전 요구 불일치)이 났습니다.
- `uv`로 신규 소스 폴더에서 **편집 모드 설치**하니 패키지 67개 설치에 성공했습니다.

```bash
# 서버 Ubuntu, 신규 소스 폴더에서
uv pip install --python <서버_홈>/hermes-new/.venv/bin/python -e .
```

> 설치 성공 ≠ 런타임·모델 호환성 입증입니다.

### 3.3 신규 환경으로 명령 보내기 — `HERMES_HOME` 지정

신규 환경의 모든 명령 앞에 **신규 데이터 폴더를 가리키는 환경변수**를 붙입니다. 이것을 빠뜨리면 기존 환경을 건드릴 수 있습니다.

```bash
HERMES_HOME=<서버_홈>/hermes-new/data <서버_홈>/hermes-new/.venv/bin/python <서버_홈>/hermes-new/hermes-agent/hermes <하위명령>
```

### 3.4 Claude 구독(DirectSDK) 연결

1. 서버에서 Claude Code 로그인 상태 확인: `claude auth status` → `loggedIn: true`, 구독 종류 확인(계정 이메일·조직 ID는 기록하지 않음)
2. 공식 플러그인 설치 → 활성화

```bash
HERMES_HOME=<서버_홈>/hermes-new/data <…>/hermes plugins install claude-subscription-directsdk
HERMES_HOME=<서버_홈>/hermes-new/data <…>/hermes plugins enable claude-subscription-directsdk-experimental
```

- 설치 직후 `installed but not enabled`가 나오는 것은 **정상**입니다.
- 신규 환경에서 `auth status`가 로그아웃으로 보이는 것은 **DirectSDK 구독과 별개**입니다(구독 로그인은 Claude Code 쪽 인증을 사용).

### 3.5 모델 선택

- 대화형 선택 화면은 `hermes model` 명령이며, 원격에서 쓰려면 `ssh -t`(터미널 할당)가 필요합니다.
- 구독 기반으로 바코1(Claude), 지코1(GPT Codex)을 설정했습니다. **선택 화면의 구체 조작은 기록에 없어** 이 문서에는 적지 않았습니다(12장).

## 4. 팀 정책(SOUL.md)

신규 환경 데이터 폴더의 `SOUL.md`에 팀 정책을 둡니다. 핵심만 옮깁니다(영문 원문의 취지).

- 한국어로 답하고 초보자도 알게 설명한다.
- 단순 질문은 바코1이 **혼자** 처리한다.
- 중요·복잡·불확실한 질문은 먼저 **바코1이 자기 분석**을 하고, `delegate_task`로 지코1에게 **독립 분석**을 요청한다. 이때 **바코1의 잠정 결론은 알려 주지 않는다.**
- 두 분석을 비교해 일치·불일치·오류·근거 부족을 가린다. 추가 비판은 **최대 2라운드**.
- 지코1이 하지 않은 답을 **지어내지 않는다.** 실패는 숨기지 않는다.
- 사용자 승인 없이 다른 에이전트를 호출하지 않는다.
- 검증된 사실 / 판단 / 미확인을 구분한다.
- 운영 환경 변경은 사용자 승인을 받는다.

### 4.1 메신저 답변 완료 표시

| 상황 | 표시 |
| --- | --- |
| 바코1이 혼자 답함 | ✅ 답변 완료 — 바코1 단독 |
| 지코1이 실제로 분석을 끝냄 | ✅ 답변 완료 — 바코1·지코1 협업 |
| 지코1 위임이 실패 | ⚠️ 답변 종료 — 지코1 검증 실패 |
| 작업이 끝나지 않음 | ⚠️ 작업 미완료 — 사유 안내 |

- 표시는 **최종 답변의 마지막 줄**에 하나만 붙입니다. 중간 진행 메시지에는 붙이지 않습니다.
- 검증된 위임 결과가 없으면 "협업 성공"을 표시하지 않습니다.

### 4.2 지침을 바꿀 때의 안전 절차 (기록된 방식)

1. **변경 전 백업 복사**(`cp -p --update=none`) → 같은 내용인지 비교(`MATCH: YES`)
2. 파일 수정
3. **이미 열려 있던 세션**은 예전 시스템 프롬프트를 재사용할 수 있으므로, 세션의 프롬프트 갱신 명령으로 새 지침을 반영

```bash
HERMES_HOME=<서버_홈>/hermes-new/data <…>/hermes sessions refresh-prompts --session <세션_ID>
```

> 지침이 바뀐 것과 에이전트가 새 지침으로 움직이는 것은 다릅니다. 반영 후 **실제 답변으로 확인**합니다.

## 5. 메신저(Telegram) 연결

- **일반협업팀 전용 새 봇**을 만들어 기존 봇과 분리했습니다. 기존 Gateway·봇 토큰·Google Workspace 설정은 건드리지 않았습니다.
- 봇 이름·허용 사용자 ID·토큰은 이 문서에 싣지 않습니다(`<봇_이름>`).
- 점진적 출력(스트리밍) 설정: 설정 파일을 **먼저 복사해 백업**한 뒤 아래 값을 확인했습니다.

```yaml
streaming:
  enabled: true
  transport: auto
```

- 결과: 답변이 조금씩 나타나는 동작을 사용자가 확인했습니다.
- 확인한 것: 신규 봇으로 실제 송수신, 바코1 한국어 응답, 완료 표시 출력(PC 웹 클라이언트 기준). **스마트폰 앱에서의 별도 시험은 하지 않았습니다.**

> 봇 생성·토큰 등록의 구체 절차는 기록이 없어 적지 않았습니다.

## 6. 서비스 운영

### 6.1 상태 조회 (조회 전용)

```bash
systemctl --user show hermes-general-gateway.service -p ActiveState -p SubState -p MainPID -p Result --no-pager
```

정상 기대값: `active`, `running`, 0이 아닌 PID, `success`.

```bash
journalctl --user -u hermes-general-gateway.service -n 35 --no-pager
```

> 로그를 공유할 때는 **토큰·개인정보를 먼저 가립니다.**

### 6.2 시작·정지 (실행 전 사용자 승인)

```bash
systemctl --user stop hermes-general-gateway.service
systemctl --user start hermes-general-gateway.service
```

- 2026-11-12 정지 때 SIGTERM 이후 **종료 코드 1**로 서비스가 `failed`로 남았고, 다시 시작하면 정상 복귀했습니다. **종료 코드 1의 원인은 확인하지 못했습니다.**
- 정지 후에는 신규 환경 프로세스가 남지 않았는지 확인합니다.

```bash
pgrep -af '<서버_홈>/hermes-new/(.venv/bin/python|hermes-agent/hermes)' || true
```

(출력이 없으면 남은 프로세스 없음)

### 6.3 재시작 뒤 확인

1. 서비스 `active/running`
2. 로그에서 `Connected to Telegram (polling mode)` 확인
3. 메신저에서 실제 질문 → 응답과 완료 표시 확인

## 7. 지코1 위임 검증하는 법

- 설정에서 **위임 경로가 지코1 프로필을 가리키는지** 보는 것만으로는 부족합니다.
- 실제 위임 기록(위임 ID, 모델, 상태 `completed`, 시작·완료 시각, 작업 로그)을 **열어서** 확인했습니다. 이번 기록에서는 위임 3건이 완료로 확인되었고, 한 건은 약 30초 만에 완료되었습니다.
- 보조 인증(예: 별도 포털)에 대한 경고 로그가 있어도 **Codex 기반 위임의 성공 기록과 구분**해서 판단합니다.

## 8. 칸반(B1~B7)으로 독립 분석하기 — 요약

- 보드 하나를 만들고, 카드마다 **담당 프로필**(바코1 또는 지코1)과 모델 경로를 지정합니다.
- 카드 순서: B1 바코 독립 → B2 지코 독립 → B3 바코가 지코 비판 → B4 지코가 바코 비판 → B5 바코 수정 → B6 지코 수정 → B7 바코 최종 종합.
- 완료 후 확인: B7이 `done`, 종료 코드 0, 최종 산출물 첨부 존재.
- 카드 작업이 끝난 뒤 **남은 보조 프로세스**(`kanban tail` 6개)가 있어 사용자 승인 후 종료했고, 재조회로 신규 환경 관련 실행 프로세스가 없음을 확인했습니다.
- 이 파이프라인의 **한계**(통계적 독립이 아님, 일치는 약한 증거, 비교 기준 없음, 비용 미측정)는 「AI 협업 운영 매뉴얼」 7장에 있습니다. B7 **최종 본문 전체에 대한 독립 내용 감사는 하지 않았습니다.**

## 9. 백업

### 9.1 무엇을 언제 백업했나

| 구분 | 시점 | 내용 |
| --- | --- | --- |
| 1차 기준백업 | 신규 환경 구축·칸반 검증 직후 | 신규 환경 전체 |
| 2차 정상상태백업 | 메신저 연동·지침 갱신 후 | 신규 환경 전체 + Gateway 서비스 파일 |

- 신규 환경 전체 약 2.7GB(프로그램 1.8GB, 데이터 717MB, 가상환경 212MB), SQLite DB 8개
- 2차 백업 파일 약 1.8GB, **권한 600**

### 9.2 만드는 법 (2차 백업에 실제 쓴 방식)

1. 신규 Gateway **만** 정지(사용자 승인) → 잔여 프로세스 없음 확인
2. 권한을 제한해 압축

```bash
(umask 077; tar -czf <서버_홈>/<백업_폴더>/<백업이름>.tar.gz -C <서버_홈> hermes-new .config/systemd/user/hermes-general-gateway.service)
```

3. 압축 검사 → 해시 파일 생성 → 해시 검증

```bash
gzip -t <서버_홈>/<백업_폴더>/<백업이름>.tar.gz
(cd <서버_홈>/<백업_폴더> && umask 077 && sha256sum <백업이름>.tar.gz > SHA256SUMS.txt)
(cd <서버_홈>/<백업_폴더> && sha256sum -c SHA256SUMS.txt)
```

정상 출력: `<백업이름>.tar.gz: OK`

4. Gateway 다시 시작 → 6.3의 확인

> 백업을 위해 Gateway를 멈추면 서비스가 잠시 중단됩니다. 시간을 정해 승인받고 하세요.

### 9.3 PC에도 보관하기 (1차 백업에서 실제 수행)

- 서버 파일을 메인 PC의 다른 드라이브로 복사한 뒤 **양쪽 해시가 같은지** 확인했습니다.

```powershell
(Get-FileHash -LiteralPath "<PC_백업_경로>\<백업이름>.tar.gz" -Algorithm SHA256).Hash
```

값이 서버의 `<64자리_해시값>`과 같아야 합니다.

### 9.4 보안 주의

- 이 백업은 **암호화되어 있지 않습니다.** 토큰·OAuth·대화 기록이 들어 있을 수 있으므로 **외부 공유 금지**, 접근 권한 제한(600/700).
- PC 쪽 보관 드라이브의 보안은 별도로 점검해야 합니다.
- 다른 팀용 복제본을 만들 때 **토큰·세션·로그·개인정보를 그대로 넣지 않습니다.**

## 10. 복원 절차 — 계획만 있음, 실행하지 않았음

> **이 장의 명령은 검토용 예시입니다. 실제 복원 시험은 이번 기록에서 수행하지 않았고, 복원 성공을 보증하지 않습니다.**

### 10.1 복원 전 확인

1. 원본 `hermes-new`가 존재하는지 확인하고 **덮어쓰지 않는다.**
2. **기존 `.hermes`에는 절대 풀지 않는다.**
3. 실행 중 프로세스·Gateway·예약 작업·열린 DB 확인
4. 여유 디스크·권한 확인
5. `tar -tzf`로 목록이 `hermes-new/`로 시작하는지 확인
6. 현 상태를 한 번 더 백업

### 10.2 안전한 순서

1. 사용자 승인 → 신규 Gateway만 정지, 잔여 프로세스 확인
2. 백업 SHA-256 확인
3. **운영 경로가 아닌 임시 폴더에 시험 압축 해제**

```bash
mkdir -m 700 <서버_홈>/restore-test-<날짜>
tar -C <서버_홈>/restore-test-<날짜> -xzf <서버_홈>/<백업_폴더>/<백업이름>.tar.gz
```

4. 파일 구조·권한·인증·SQLite DB·서비스 경로 검토 (가상환경의 **절대경로**, `HERMES_HOME`, OAuth, 권한은 별도 확인 필요)
5. 기존 신규 폴더는 지우지 말고 **별도 보존**한 뒤, 승인 하에 실제 복원
6. 서비스·메신저·바코1·지코1 위임·기록 **재검증**

### 10.3 오류 대응

| 증상 | 하지 말 것 | 할 것 |
| --- | --- | --- |
| `sha256sum -c` 실패 | 해시 파일을 고쳐서 맞추기 | 파일 사용 중단, 원본과 비교, 정상 백업에서 다시 복사 |
| `tar -tzf` 오류 | 그대로 풀어 운영에 투입 | 압축 손상 가능성, 중단 |
| `Permission denied` | `chmod 777` | 소유권·권한 확인 |
| `No space left on device` | 원본·기존 백업 삭제 | 저장 공간 확인 |
| 복원 후 인증 실패 | 인증 파일 덮어쓰기·키 갱신 | 인증 경로를 읽기 전용으로 점검 |
